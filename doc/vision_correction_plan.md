# 카메라 보정 구현 계획 — eye-in-hand D405

기존 `vision_inspection_plan.md` / `vision_camera_setup.md`를 **대체하지 않고
전제를 정정한다.** 두 문서는 외부 고정 카메라를 전제로 쓰였고, 실물은 그것이
아니다 (§0). 측정 원리·태그 운용·안착 판정 논의는 그대로 유효하므로 계속
참조한다. 바뀌는 것은 **캘리브레이션 형식과 측정 흐름**이다.

---

## 0. 전제 정정 — 문서와 실물의 불일치

`vision_inspection_plan.md:206`은 이렇게 확정하고 있다:

> **확정 사항 (Rev 3): 외부 고정 카메라 1대 + AprilTag(tag36h11)를 쓴다.**

그리고 `:217`에서 eye-in-hand(M1)를 "손목 D405를 병용할 때만 필요. 외부
카메라만 쓰면 **불필요**"로, `:222`에서 "손목에 카메라가 없으므로"라고 적었다.

**실측 결과 이 전제가 성립하지 않는다.**

| 항목 | 문서 전제 | 실측 |
|---|---|---|
| 카메라 대수 | 외부 고정 1대 | **D405 1대뿐** (`lsusb`: `8086:0b5b`, serial `315122272475`) |
| 장착 | 브레드보드 고정 | **손목 장착** (사용자 확인) |
| 캘리브레이션 | eye-to-hand → `T_base_cam` | **eye-in-hand → `T_ee_cam`** |
| 외부 카메라 | 존재 전제 | **존재하지 않음** |

문서는 8/12 작성, AprilTag 시트(`doc/apriltags/`, 바닥 100 mm 태그 + 홀더
10 mm 태그)는 8/13 작성이다. 태그 구성 자체가 이미 eye-in-hand 배치다 —
**고정 태그 + 움직이는 카메라**. 즉 실제 작업은 이미 eye-in-hand로 갔고
문서만 남아 있다.

**이 계획은 eye-in-hand를 기준으로 한다.** 외부 카메라가 나중에 추가되면
§6에 적은 대로 이 계획 위에 얹는다 (버리는 작업 없음).

### 0.1 전제가 바뀌면서 좋아지는 것

문서가 걱정하던 두 문제가 **사라진다**:

- **로봇 팔 가림** (`vision_camera_setup.md:142`, "30° 비스듬") — 카메라가
  손에 있으므로 팔이 시야를 가릴 일이 없다. 마운트 각도 타협이 불필요하다.
- **랙과 측정 홀더를 한 시야에** (`:529`) — 카메라가 따라가므로 한 대로
  둘 다 본다. 배치 제약이 없다.

그리고 결정적으로:

**기존 `Robot:Vision:DX/DY/DZ` 훅이 eye-in-hand 출력과 정확히 맞는다.**

```rust
// sequence.rs:505 — 보정은 TCP-local 프레임
self.model.apply_cartesian_offset(base, offset, /* z_global */ false, label)
```

`corrected()`는 티칭 웨이포인트의 FK 포즈에 **TCP 로컬**로 offset을 곱한다.
eye-in-hand 카메라의 측정값은 툴에 붙어 있으므로 그대로 TCP-local이다.
외부 고정 카메라였다면 base 경유 변환이 필요했고, 그 변환에
`T_base_cam` 오차가 통째로 실렸을 것이다. **훅을 고칠 필요가 없다.**

## 2. 좌표계와 미지수

```
        T_base_ee        FK로 계산 (관절각 → 기지)
   base ──────────► ee ──────────► cam ──────────► tag
                    T_ee_cam        T_cam_tag
                    ▲               ▲
                    │               └── 매 프레임 측정 (solvePnP)
                    └── 미지수. 1회 캘리브레이션 (§3)
```

**보정에 실제로 필요한 것은 절대 포즈가 아니다.** 티칭된 `above` 자세에서
태그를 보고, "기대 위치 대비 얼마나 어긋났나"만 구한다:

```
d_cam   = T_cam_tag(측정) 의 위치 − T_cam_tag(기준, 티칭 시 저장) 의 위치
d_tcp   = R_ee_cam · d_cam                    ← 회전만 쓴다
→ Robot:Vision:DX/DY/DZ  (mm, TCP-local)
```

**`T_ee_cam`의 병진 성분은 1차적으로 상쇄된다** — 같은 카메라가 기준과 측정을
모두 찍기 때문이다. 회전 `R_ee_cam`만 정확하면 된다. 이것이 eye-in-hand 상대
측정이 절대 캘리브레이션 정확도에 둔감한 이유이고, `max_correction: 3.0` mm
같은 좁은 한계를 걸 수 있는 근거다.

> 이 성질은 §5(지그 로컬라이제이션)에서는 성립하지 않는다. 거기서는 절대
> `T_base_rack`이 필요하고 `T_ee_cam`의 병진 오차가 그대로 실린다. **그래서
> §4까지와 §5 이후는 요구 정확도가 다르다.**

## 3. Phase 0 — 측정 기반 (선행 필수)

이 단계가 끝나기 전에는 그 어떤 보정도 의미가 없다.

### 3.1 내부 파라미터 확보

**현재 얻을 수 없다.** IOC가 intrinsics를 PV로 내보내지 않는다:

```
RS405:cam1:RSFx_RBV   → Channel connect timed out: not found
RS405:cam1:RSDepthUnits_RBV → 0.0001      (이건 있음)
```

드라이버는 값을 갖고 있다 (`epics-rs-iocs/drivers/d435i/src/types.rs`에
intrinsics 타입 존재). 세 선택지:

| 안 | 방법 | 평가 |
|---|---|---|
| **A** | IOC에 `RSFx/RSFy/RSPpx/RSPpy/RSCoeff` PV 추가 | **권장.** 드라이버가 이미 보유. 변경 국소적. 장치 교체 시 자동 추종 |
| B | 비전 노드가 pyrealsense2로 직접 조회 | 카메라를 IOC가 배타 점유 중이라 충돌 |
| C | 체커보드로 독립 캘리브레이션 | 공장값보다 정확할 수 있으나 공수 큼. A 검증용으로 유용 |

**A로 진행하고, C를 1회 교차검증으로 쓴다.** 두 값이 크게 다르면 A를 믿지
않는다.

⚠ `dist_coeffs = zeros(5)`를 그대로 두지 말 것. D405가 왜곡 보정된 프레임을
주는지 실제 계수로 확인하고, 0이 아니면 반영한다.

### 3.2 태그 검출 파이프라인

```
RS405:image1:  ─(CA 또는 PVA)─►  비전 노드  ─► tag36h11 검출 ─► solvePnP
                                     │                              │
                                     └──────── Robot:Vision:* ◄─────┘
```

구현 언어는 Python (기존 `robot_gui`가 이미 pyepics 기반, `robot_gui` conda
env 재사용 가능). `pupil-apriltags` 또는 `cv2.aruco.DICT_APRILTAG_36h11`.

### 3.3 태그 크기 결정 — 시험띠로 실측

10 mm 태그가 실제로 검출되는지는 **계산이 아니라 측정으로** 정한다.
`doc/apriltags/`의 시험띠 (id 100–104, 10/15/20/25/30 mm)가 이 용도다.

개략 계산으로 예상되는 문제 (실측으로 확정할 것):

IOC의 실측 intrinsics(fx 393.284, cx 321.745, fy 392.673, cy 246.323)로
계산한 값이다. 사양서의 87°가 아니라 **78.3° × 62.8°** 이다:

```
HFOV = atan(cx/fx) + atan((640-cx)/fx) = 39.28° + 38.98° = 78.3°
VFOV = atan(cy/fy) + atan((480-cy)/fy) = 32.09° + 30.75° = 62.8°

640×480, 작업거리 150 mm
→ 시야 폭 = 150·(tan39.28° + tan38.98°) ≈ 244 mm → 0.38 mm/px
→ 10 mm 태그 ≈ 26 px
```

tag36h11은 테두리 포함 10×10 셀이라 26 px면 셀당 2.6 px — **경계선상**이다.
대응책 두 가지:

- **IOC 해상도를 1280×720으로 올린다** (st.d405.cmd:47이 지원 명시)
- 또는 더 큰 태그를 쓴다 (시험띠가 답을 준다)

실제로는 10 mm 태그를 붙일 자리가 없어 **100 mm 한 장을 바닥에 고정**했고,
작업거리 ≈ 290 mm에서 0.74 mm/px로 관측된다.

## 4. Phase 1 — hand-eye 캘리브레이션 (`T_ee_cam`), 평생 1회

### 4.1 절차 — 데몬의 `CalibMode = 3`

수집은 별도 도구가 아니라 **`robot-sequencer` 데몬 자체**가 한다. 로봇은
RTDE 클라이언트를 하나만 받으므로, 별도 바이너리로 수집하려면 프로덕션
데몬을 내려야 하고 — 카메라를 보정하려고 그 카메라에 의존하는 데몬을
죽이는 것은 순서가 거꾸로다.

```bash
caput Robot:CalibMode 3        # Hand-Eye Calib
caput Robot:Trigger 1          # 1회차: aiming hold (jog 가능, 1 Hz 검출 로그)
# JogX/Y/Z로 태그를 화면 중앙에 맞춘다
caput Robot:Trigger 1          # 2회차: 수집 시작
```

트리거가 2회인 것은 다른 캘리브레이션 모드와 같은 이유다. idle 트리거
대기(`wait_for_trigger(false)`)는 jog를 서비스하지 않는다 — 그 자리는 티칭된
standby 자세이고 거기서 jog를 허용하면 시퀀스의 시작점이 움직인다. 조준은
모드가 정해진 뒤의 hold에서 한다. hold 중에는 검출기가 이미 떠 있으므로
1초마다 태그 위치를 로그로 되돌려준다 — "화면에 보인다"와 "검출기가 풀 수
있다"는 다른 주장이고, 수집을 성립시키는 것은 후자다.

바닥 고정 태그(**id 0, 100 mm**)를 브레드보드에 볼트 고정한다. 데몬은
2회차 트리거 시점의 자세를 home으로 잡고, 툴 자체 축(x/y/z) 둘레로 회전한
12자세를 돌며 각 자세에서:

1. 관절각 기록 → FK로 `T_base_ee`
2. 태그 관측 → solvePnP → `T_cam_tag`

자세마다 home으로 복귀하므로 검출 실패가 누적되지 않고, 모든 이동은
계획(RRT) 이동이 아니라 직선 보간 이동이고(§4.1 각주), 충돌 검사는
시퀀스와 같은 씬을 쓴다. 결과는
`handeye.out_dir/samples_<timestamp>.yaml` (캡처마다 새 이름).

**공전(orbit)이 아니라 제자리 회전인 이유.** `calibrateHandEye`가 원하는
것은 회전 다양성이지 병진이 아니고, 셀이 좁다. 290 mm에서 100 mm 태그는
78°×63° 시야 안에서 약 ±10°만 차지하므로 툴은 태그가 프레임을 벗어나기
전까지 수십 도를 돌 수 있다 — 그리고 툴 회전은 카메라를 마운트 오프셋
만큼(수십 mm) 옮길 뿐이어서, 같은 각도의 공전이 요구하는 ~100 mm 이동과
비교가 안 된다.

수집 자세 수(12) × 3축은 고정이고, 각도만 `handeye.angle_deg`로 조절한다.
축이 3개인 것은 필수다 — 회전축을 공유하는 두 상대운동은 AX = XB에서
축퇴(degenerate)이고, 이것이 "그럴듯한 오답"이 나오는 전형적 경로다.

```python
# eye-in-hand: 반환값이 곧 T_ee_cam
R_cam2gripper, t_cam2gripper = cv2.calibrateHandEye(
    R_gripper2base, t_gripper2base,     # invert 하지 않는다
    R_target2cam,   t_target2cam,
    method=cv2.CALIB_HAND_EYE_TSAI)
```

⚠ **`invert_gripper2base = False`.** 구 코드의 이 플래그는 eye-to-hand용이다
(`hand_eye_calibration_node.py:463`). eye-in-hand에서 켜면 결과가 조용히
틀린다 — 수렴은 하되 값이 틀리므로 residual만으로는 못 잡는다.

**회전 다양성이 정확도를 지배한다.** 위치만 옮기고 자세를 안 바꾸면
`calibrateHandEye`는 병조건이 된다. 태그를 화면 중앙에 맞춰 놓으면 이 셀
에서도 ±29°/±21°까지는 실측으로 확보된다.

> 여기서 §0.1의 level-tool 제약(`scene.rs:49`, ±3°)이 걸린다. 캘리브레이션
> 자세는 정확히 그 제약이 금지하는 툴 회전이다. 이 문서는 원래
> `Motion::suspend_level_tool`이 돌려주는 가드로 수집 동안만 제약을 끄는
> 설계를 적었으나, **그 함수는 구현되지 않았다.** 실제로 만들어진 것은
> 제약을 끄지 않고 아예 지나가지 않는 쪽이다: 제약은 `Motion::move_planned`
> 에서만 읽히고 수집의 모든 이동은 `move_direct`(직선 보간, 충돌 검사는
> 동일 씬)라 애초에 평가되지 않는다. 끄고 켜는 상태가 없으니 복원 누락도
> 없다.
>
> 대신 이 설계가 옮겨 놓은 위험은 다른 곳에 있었다. 제약을 지나가는 것은
> 수집 중의 이동이지 **수집이 끝난 뒤의 팔**이 아니다. 조준 자세는 level에서
> 수십 도(실측 70.8°) 벗어나 있고, 초기 구현은 팔을 거기 둔 채 트리거 대기로
> 돌아갔다 — 다음 시퀀스의 step 1이 `start or goal state is itself invalid`로
> 계획에 실패하고 데몬이 종료한다. `Sequence::handeye_return`이 모드 진입
> 자세로 되돌리는 것으로 닫혔고, `move_planned`은 시작 자세를 자기가 계획할
> 제약으로 먼저 판정해 다른 경로로 비-level이 된 경우도 이름을 대게 했다.

### 4.2 검증 — residual만 믿지 않는다

`calibrateHandEye`는 틀린 입력에도 답을 낸다. **독립 검증**이 필수다.
`tools/handeye/solve.py`가 이 둘을 자동으로 낸다:

- 여러 방법(Tsai / Park / Horaud / Daniilidis) 결과가 서로 **2 mm, 1° 이내**
  로 일치하는지 — 흩어지면 데이터가 나쁜 것이다
- leave-one-out: 한 자세를 빼고 적합한 뒤, 뺀 자세로 `T_base_tag`를 예측해
  나머지의 평균과 비교. 적합에 쓴 자세의 residual과 달리 이것은 실제
  측정이 지게 될 오차다

4점 태그의 reprojection error는 **정확도 지표가 아니다** — 미지수와 관측
수가 거의 같아 언제나 작게 나온다.

### Phase 1 완료 기준

- [ ] 검증셋 5자세에서 예측-실측 위치 오차 **< 2 mm**, 회전 오차 **< 1°**
- [ ] 4개 방법의 해가 서로 2 mm / 1° 이내
- [ ] `T_ee_cam`을 YAML로 저장 + 측정 일자·자세 수·residual 기록
- [ ] URDF에 카메라 링크 추가 (측정된 `T_ee_cam`으로) — scene/충돌 검사에서
      카메라 몸체가 고려되도록

## 11. 미확정 — 실측해야 정해지는 값

문서가 추정치로 적고 있으나 **아직 측정되지 않은** 것들.

- 작업거리에서 안정 검출되는 최소 태그 크기 (10 mm로 되는가) — 시험띠 미실행,
  현재는 100 mm 한 장으로 우회
- `min_correction` / `max_correction`의 근거 있는 값 (현재 0.05 / 3.0 mm는 추정)
- ~~D405 최소 작업거리(사양 ~70 mm)와 티칭 `above` 자세의 실제 거리 관계~~
  실측·계산 완료 (`T_ee_cam` + 티칭 자세 FK): 카메라–파지점 광축 거리가
  `standby` 136.0 mm, `above` **63.3 mm**, `on_position` 62.2 mm.
  `above`는 D405 스테레오 최소거리 아래라 **깊이가 나오지 않는다**
  (모노 프레임은 별개 문제). `above_y_offset`이 −5 mm 툴 y = 수직
  방향이라 `on_position`과 광축 거리가 1.1 mm밖에 차이나지 않는 것이
  원인. 보정 관측은 `standby`에서 해야 하고, 거기서 Ø25.1 mm 특징이
  72 px로 잡힌다.
- 640×480 15 fps로 충분한지, 아니면 해상도·프레임률 상향이 필요한지
- ~~`min_correction` / `max_correction`의 근거~~ → 아래 항목으로 대체. §12.3이
  잡음 바닥(0.0017 mm)과 팔 재접근 편차(0.070 mm, n=1)를 각각 재서, 데드밴드가
  걸러야 할 것이 센서가 아니라 **팔**임을 보였다. 0.05 mm는 재접근 편차보다
  작아 매 사이클 헛보정을 낸다 — Phase 2에서 σ를 쌓아 확정할 것

확정된 것(더는 추정이 아님):

- intrinsics: fx 393.284 / fy 392.673 / cx 321.745 / cy 246.323 → HFOV 78.3°
  (사양값 87°는 **틀렸다**)
- 왜곡 모델 규약: IOC가 보고하는 `BrownConradyInverse`는 **OpenCV 정방향
  Brown-Conrady와 같다**. 이름으로 추정하지 않고 `librealsense2.so`에 직접
  물었다 — 같은 계수로 `rs2_project_point_to_pixel`이 `cv2.projectPoints`를
  `RS2_DISTORTION_BROWN_CONRADY`에서 **정확히(0.0000 px)** 재현하고,
  `INVERSE_BROWN_CONRADY`에서는 **0.0223 px** 차이가 난다. 그 0.0223 px는
  librealsense가 INVERSE를 `MODIFIED_BROWN_CONRADY`와 **동일하게** 투영하기
  때문에 생기는 librealsense 내부 분기 차이지, OpenCV와의 규약 차이가 아니다
  (이전 판은 "접선항 적용 순서 차이"라고 적었으나 그건 측정된 바 없는
  추정이었다). "Inverse"는 OpenCV 기준이 아니라 `MODIFIED_BROWN_CONRADY`의
  역투영 기준 이름이다. 따라서 계수를 그대로 solvePnP에 넣는 것이 맞고,
  버리면 모서리에서 5.8 px = 290 mm에서 4.3 mm가 틀어진다.
  재현: `tools/handeye/check_distortion_model.py`
- 검출 재현성: 정지 태그 20회 연속 검출에서 σ = (0.015, 0.008, 0.056) mm,
  20/20 서로 다른 프레임. 단 이는 아래 두 버그를 고친 뒤의 값이다 —
  pyepics가 `use_monitor=False` 없이는 캐시를 돌려주는 문제, 그리고
  cv2 기본값 `CORNER_REFINE_NONE`이 코너를 정수 픽셀로 양자화하는 문제.
  둘 다 "완벽한 재현성"으로 위장하며, 그대로 뒀다면 `T_ee_cam`에 0.74 mm급
  오차가 조용히 실렸을 것이다.

## 12. 무태그 특징 추출 — 홀더를 인식하지 않는 쪽으로 (2026-08-14 실측)

§10이 마지막까지 ⛔로 남겨둔 항목이다. 막힌 이유는 "금속 홀더를 어떻게
인식하나"였고, 풀린 방식은 **인식하지 않는 것**이다. 보정에 필요한 것은
절대 포즈가 아니라 기준 대비 어긋남뿐이므로(§2), 문제를 물체 인식에서
영상 정합으로 바꾸면 정반사도 무태그도 장애물이 아니다 — 정반사는 모델
기반 검출을 깨뜨리지, 같은 자세에서 반복 촬영한 두 장의 상호상관을
깨뜨리지 않는다.

### 12.1 depth는 재는 데 못 쓰지만 가르는 데는 쓴다

standby에서 찍은 전체 프레임 depth 히스토그램:

```
   75 mm  16779 px   ← 홀더 스택
  150 mm    860 px
  ────────  없음  ────────  525 mm 폭의 공백
  675 mm    247 px
  825 mm+  .......  ← 배경 전부
```

50–250 mm 게이트가 프레임의 **6.23%(19145 px)만 남기고** 어수선한 배경을
통째로 지운다. 남는 이물은 프레임 우하단 모서리의 1505 px 한 덩어리뿐이고,
컬럼과 연결되지 않아 버려진다.

금속에서 depth가 1.83 mm 치우침·8.48 mm 산포였던 것이 여기서는 무해하다.
**재는 게 아니라 가르는 용도**이고 갈라야 할 간격이 525 mm다. 이 구분이
이 절 전체의 요지다 — depth의 실패는 metrology로서의 실패였지 segmentation
으로서의 실패가 아니었다.

### 12.2 "빈 부분은 어둡다"는 이 하드웨어에서 성립하지 않는다

보어가 광 트랩이라 어둡게 잡힐 것이라는 기대는 **실측으로 기각**된다.
depth ROI 안 mono는 24979 px, 중앙값 124이고 80 미만이 1890 px(7.6%),
60 미만이 398 px(1.6%)다. 60 미만으로 잡히는 것은 퍽 림과 시트가 만나는
그림자 호뿐이고 홀더당 100–250 px짜리 얇은 초승달이다. 실험실이 확산광으로
밝고, 이 홀더는 카메라 쪽으로 깊은 공동을 내주지 않는다.

따라서 "빈 부분"의 판별자는 **밝기가 아니라 거리**여야 한다. 12.1이 그것이다.

### 12.3 추정기의 잡음 바닥과, 그보다 40배 큰 것

팔을 홀더 3 standby에 세워둔 채 20프레임, ROI는 12.1의 게이트,
정합은 `cv2.findTransformECC(MOTION_TRANSLATION)`:

```
게이트 면적       4697 px, σ 79 px (1.7%)
ECC 병진 σ        (0.0050, 0.0036) px = (0.0017, 0.0012) mm
        p-p       (0.022, 0.014) px
```

이 숫자가 위장이 아닌지 따로 확인했다 — 이 저장소에서 "완벽한 재현성"은
이미 두 번(pyepics 캐시, `CORNER_REFINE_NONE`) 버그의 가면이었다.
ArrayCounter가 2씩 전진해 전부 다르고, 창 안 픽셀의 75%가 프레임마다
바뀌며, 화소별 시간 σ는 1.41 DN이다. 잡음은 실재하고 추정기가 4700 px에
걸쳐 평균해서 이긴다: 1.41 DN / (5 DN/px × √4700) ≈ 0.004 px로, 실측
0.005 px와 맞는다.

**그런데 지배하는 것은 센서가 아니라 팔이다.** 같은 자세를 떠났다가
(standby → above → retreat → 계획 이동) 돌아와 다시 찍은 프레임은
기준 대비 **0.070 mm**(dx 0.013, dy 0.069, ECC 상관 0.980) 어긋나 있었다.
n = 1이라 σ가 아니라 한 번의 차이지만, 잡음 바닥의 40배이고
`min_correction: 0.05` mm보다 크다. 즉 지금 데드밴드는 팔의 재접근 편차를
걸러내지 못하고 매 사이클 헛보정을 낸다. 데드밴드가 걸러야 할 대상이
무엇인지가 이 측정으로 바뀌었다.

### 12.4 훅이 걸린 자세에서는 대상이 보이지 않는다

`sequence.rs:236-238`은 step 2(`holder_above`)를 끝낸 직후 측정한다.
홀더 3의 `above`에서 실제로 찍어 확인한 결과:

- 파지점(`on_position`, `above_y_offset` −5 mm 만큼 툴 +y)은
  **(337, 535)** 에 투영된다 — 480행짜리 프레임의 아래 모서리보다 **56행 아래**.
  ee 원점조차 (337, 508)로 프레임 밖이다.
- 그 거리에서 프레임이 덮는 툴 y 범위는 −41 mm ~ −3.7 mm, 즉 대상의
  **위쪽 3.7–41 mm** 다. 홀더 피치가 30 mm이므로 화면 중앙을 채우는 원반은
  **한 칸 위 홀더의 퍽**이다 — 홀더 3의 `above`에서 실제로 보이는 것은
  홀더 2이고, 투영 (335, 363)이 그 원반 위에 정확히 떨어진다.
- depth도 없다. 유효 화소가 69% → 51%로 떨어지고, 근거리 클러스터가
  사라지며(75 mm 빈 16779 → 300 px), 10072 px가 0–75 mm — 스테레오 하한
  아래다. 50–250 mm 게이트는 최대 성분이 34.3%인 얼룩이 되고 그 성분은
  **뒤쪽 벽** 위에 있다. 게이트가 약해지는 정도가 아니라 틀린 답을 준다.

"보이지 않는다"보다 나쁘다. 소박한 검출기라면 이웃 홀더에 확신을 갖고
붙어 엉뚱한 보정을 낼 것이다. 훅은 **standby로 옮겨야** 한다 — 광축 거리
136.0 mm, Ø25.1 mm 특징이 72 px, 12.1–12.3의 숫자가 전부 그 자세의 것이다.

→ 옮겼다. §13.

### 12.5 옮기기 전에 고쳐야 할 것 — `above`에서는 계획 이동이 안 된다

위 촬영을 하려고 팔을 `above`에 세워둔 김에 드러난 것이다.
`above`에서 출발하는 `move_planned`는

```
holder_standby: planning failed: planner 'rrt_connect' failed:
  planning failed: start or goal state is itself invalid
```

로 실패한다. §4.1의 level-tool 가드는 통과했으므로(그랬다면 그 이름을
댔을 것이다) 제약 문제가 아니라 상태 유효성 문제다. 정상 시퀀스가 이걸
못 만난 이유는 **계획 이동이 `above`에서 출발한 적이 없기 때문**이다 —
계획 이동은 1/7/18뿐이고 각각 standby·retreat·sh_standby에서 출발하며,
above↔on은 전부 cartesian이다. 빠져나온 경로도 시퀀스 자신의 것이었다:
step 6(`above`→`retreat`, cartesian) 뒤 step 18(계획 이동 → standby, 0.09 s).

훅을 어디에 두든, 그리고 관측을 위해 어떤 자세에 잠깐 머무르든, 그 자세에서
복귀가 가능한지가 선행 조건이다.

### 12.6 이 복구 과정이 드러낸 운영상 결함 셋

전부 이번 한 번의 촬영에서 실제로 겪었다.

1. **계획 실패가 데몬을 죽인다.** 팔은 멀쩡히 서 있는데 데몬이 나가고
   RTDE 연결이 끊긴다. hand-eye 수집 실패는 이미 데몬을 죽이지 않도록
   고쳐져 있다(`doc/handeye_calibration.md`) — 같은 처리가 시퀀스 쪽에는
   없다.
2. **재시작이 그리퍼를 여닫는다.** 기동 로그의 "Hand-E successfully
   activated"는 Robotiq 활성화 스트로크다. 시료를 문 채 데몬이 죽으면
   재시작이 그것을 떨어뜨린다. 활성화는 이미 활성인 그리퍼에 대해
   멱등이어야 한다.
3. **PauseStep은 앞으로만 풀린다.** `wait_for_pause_step_change`에서
   빠져나오는 길은 다음 스텝으로 진행하는 것뿐이라, "여기서 멈추고
   standby로 돌아가라"를 표현할 수단이 없다. 그래서 이번에도 데몬을
   두 번 죽여야 했고, 그때마다 2번 위험을 무릅썼다.

셋은 한 사건의 세 얼굴이다: **중단 상태에서 안전 자세로 돌아가는 소유자가
없다.** 3이 없어서 죽여야 하고, 1이 죽이고, 2가 죽는 것을 위험하게 만든다.

## 13. 훅을 standby로 옮김 (2026-08-14, 12.4의 해소)

12.4가 남긴 작업을 실행했다. 옮기기 전에 12.5의 선행 조건 — "그 자세에서
복귀가 가능한가" — 는 `CalibMode = 4` 복구 모드로 해소됐고, 12.6의 결함
1·3도 같이 닫혔다(2는 열려 있다).

### 13.1 어디서 보이는지를 먼저 계산했다

12.4는 홀더 3 하나를 실제로 찍어서 얻은 결과다. 옮길 곳이 모든 홀더와
샘플홀더에서도 성립하는지는 사진이 아니라 모델로 확인했다 — URDF FK로
자세를 만들고 `T_ee_cam` + 내부 파라미터로 투영한다. 검증은 12.4의 실측과
맞는지로 했다: 계산이 `above`에서 (336, 535), 축상 63.3 mm를 내놓았고
실측은 (337, 535)였다. standby도 계산 136.5 mm / 73 px 대 실측 136.0 mm /
72 px.

| 관측 자세 | 파지점 투영 | 축상 거리 | 광축각 | 25.1 mm = ? |
|-----------|-------------|-----------|--------|-------------|
| 홀더 `above` (기존) | (336, **535**) | 63.3 mm | 35.3° | 프레임 밖 |
| 홀더 `standby` | (306, 330) | 136.8 mm | 11.2° | 73 px |
| 샘플홀더 `sh_standby` | (313, 277) | 208.8 mm | 3.7° | 48 px |

샘플홀더 쪽이 오히려 화면 중앙에 가깝다. 대신 1.5배 멀어 mm/px가 0.343 →
0.523으로 커지므로, 12.3의 ECC 잡음 바닥 0.0017 mm는 그쪽에서 0.0027 mm가
된다. 팔의 재접근 편차(0.070 mm)에 여전히 25배 눌린다.

`the_hooks_observe_from_poses_that_see_the_target`(model.rs)가 이 표를
테스트로 고정한다. 홀더 1·3·10과 샘플홀더에 대해 standby에서는 프레임 안,
`above`에서는 프레임 밖임을 함께 주장한다 — 뒤쪽 주장이 없으면 훅이 조용히
되돌아갈 수 있다.

### 13.2 파지 편차(Grip Offset)만은 옮겨도 소용없다

물린 퍽은 툴에 고정돼 있어서 팔이 어디에 서 있든 카메라와의 관계가
같다. 퍽 중심은 (336, **509**) — 프레임 아래 29행 밖이다. 다만 완전히 안
보이지는 않는다: 반경 12.55 mm 원반의 가까운 쪽 림이 (335, **405**)로
프레임 안에 들어온다. 즉 화면 맨 아래에 초승달만 걸린다.

광축에서 33°, 왜곡 모델이 가장 덜 구속된 가장자리다. 여기서 측정이
가능한지는 **재본 적이 없다** — 그래서 훅을 지우지도, 옮기지도 않고 원래
자리(스텝 5/16)에 뒀다. 자세를 바꿔도 그림이 같으므로 옮길 이유가 없다.
이 훅을 쓰려면 초승달 정합을 실측하거나, 카메라를 다시 앉혀야 한다.

### 13.3 보정량이 프레임을 달고 다니게 했다

측정 자세와 적용 자세가 달라지면서 `[f64; 3]` 세 숫자만으로는 어느 툴
프레임의 것인지 말할 수 없게 됐다. `Correction { d, frame }`이 관측 자세의
자세(quaternion)를 함께 들고 다니고, `corrected`가 적용 대상 자세의
프레임으로 회전시킨다. `combine_corrections`도 두 항(슬롯 정렬 = standby,
파지 편차 = above)을 공통 프레임으로 옮긴 뒤 더한다 — 서로 다른 프레임의
벡터를 더하던 자리다.

실제 회전량은 랙 0.79°, 샘플홀더 0.21°다. 3 mm 상한에서 41 µm이라 무시해도
당장은 티가 안 난다. 회전을 넣은 이유는 크기가 아니라, standby를 다시
티칭했을 때 조용히 틀리지 않게 하기 위해서다.

### 13.4 딸려 나온 단순화

`above`를 고쳤으니 옆으로 옮긴 뒤 내려가야 했다 — `cartesian_via`가 그
때문에 있었다. 이제 보정이 `above`로 가는 이동에 흡수되므로 하강은 다시
순수 수직이고, `cartesian_via`는 `cartesian`으로 접혔다.
