## 1. 가장 중요한 것: 카메라를 어디에 놓느냐

### 1.1 원칙 한 줄

> **재고 싶은 방향과 카메라가 보는 방향(광축)이 서로 수직이 되게 놓는다.**

카메라 1대는 **거리(깊이)를 잘 못 잰다.** 반대로 **이미지 평면 안의 위치는 아주 잘 잰다.**
차이가 크다 — 같은 카메라로 같은 물체를 봐도, 어느 축이냐에 따라 정밀도가 **10배 이상**
차이 난다.

```
카메라 ─────────▶  광축 방향 (Z)        ← 부정확  (거리, 깊이)
                   이미지 평면 (X, Y)   ← 정확    (좌우, 위아래)
```

### 1.2 이 셋업에 적용하면 → **정면 계열, 실제로는 30° 비스듬** (§1.2.3)

**⚠ Rev 3 정정**: 초판은 "퍽이 수평으로 꽂힌다"는 잘못된 가정으로 측면 뷰를 권했다.
코드 확인 결과 **수직 안착**이다:

```
above → on_position :  TCP local Y로 5 mm    ← 퍽을 포크에 내려놓음 (수직)
retreat             :  TCP local Z로 50 mm   ← 툴 축 방향 후퇴
slot pitch          :  TCP local Y로 30 mm × (N−1)   (holder_offset)
```
(`epics_triggered_sequence.cpp:1141-1144` — 오프셋은 **TCP 로컬 프레임** 기준.
`above_y_offset=-0.005`, `retreat_z_offset=-0.05`, `holder_offset=0.03`)

즉 "제대로 꽂혔나" = **퍽이 5 mm 제대로 내려앉았나** = **Y(수직)** 측정이다.
그리고 슬롯별 보정이 필요한 축은 **X(측방)** 와 **Z(깊이)** 다 (§1.2.1).

| 카메라 뷰 | 안착 Y (5 mm) | 측방 X (최대 3 mm) | 깊이 Z (최대 0.45 mm) |
|---|---|---|---|
| **정면 (권장)** | ✅ | ✅ | ❌ |
| 측면 | ✅ | ❌ | ✅ |
| 위 | ❌ | ✅ | ✅ |

→ **정면 뷰.** 안착(Y)과 가장 큰 보정축(X)을 동시에 잡는다. 포기하는 Z는 가장 작고
(0.45 mm), 지그 6-DoF 자세 피팅으로 대부분 흡수된다 (§1.2.1).

**정면 뷰 하나로 얻는 것:**
- 슬롯 10개 점유 (실루엣 있냐 없냐)
- 안착 높이 Δz (실루엣의 상하 위치) ← 판정의 핵심
- 기울기 (실루엣의 각도)
- 측방 오프셋 X (실루엣의 좌우 위치)

네 가지 전부 이미지 평면 안의 측정이라 정확하다.

### 1.2.1 기존 슬롯별 오프셋 18개의 정체 — 개체차가 아니라 기울기

`taught_waypoints.yaml` 의 손튜닝 값 (홀더 2–10, 피치 30 mm → 총 270 mm 구간):

```
홀더:   2      3      4      5      6     7     8     9    10
x:     0.3    0.5    1.5    1.5    3.0   3.0   3.0   3.0   3.0   mm
z:     0      0      0      0.2    0.25  0.3   0.35  0.4   0.45  mm
y:     보정 없음  ← 슬롯 피치 자체는 정확하다는 뜻
```

- **z**: 홀더 5부터 슬롯당 정확히 +0.05 mm. 270 mm에 0.45 mm → **0.095° 기울기**
- **x**: 270 mm에 3 mm → **0.64° 기울기**. 계단 모양(`0.3,0.5,1.5,1.5,3.0×5`)은 물리
  현상이 아니라 **손튜닝의 양자화**로 보인다

→ **10개 슬롯이 제각각 틀어진 게 아니라, 판 전체가 두 방향으로 기울어 있다.**
카메라로 랙의 6-DoF 자세를 재면 이 기울기는 **자세 파라미터가 통째로 흡수**한다.
슬롯마다 따로 재지 않아도 18개가 자세 하나로 대체된다.

**이행 시 주의 — 손튜닝값을 바로 지우지 말 것.** 그 값들은 실제 작동 결과로 수렴한
것이라 랙 기울기 + 로봇 절대 오차 + 그리퍼 편차가 **섞여** 있다. 카메라로 랙만 재면
그중 랙 성분만 본다. 순서:

```
1. 카메라 6-DoF 자세로 오프셋을 계산한다
2. 현재 손튜닝값과 비교만 한다 (아직 교체 안 함)
3. 차이가 작으면 → 기울기가 주원인 확인 → 교체
4. 차이가 크면  → 남는 차이가 로봇 절대 오차 → §1.2.2 상대 측정으로 간다
```

### 1.2.2 가장 강한 방법: 상대 측정 (look-then-move)

같은 프레임에서 **퍽과 목표 슬롯을 동시에** 보고, 둘 사이 어긋남을 직접 잰 뒤 그만큼
보정해서 하강한다. `vision_inspection_plan.md` §4.3의 Stage 2가 이것이다.

**이 셋업이 특히 유리한 이유: 두 물체가 5 mm 거리에 있다.**
`above` 포즈에서 퍽은 목표 슬롯 바로 위 5 mm다. 화면에서 거의 붙어 있는 두 물체를
재는 것이므로 — 같은 렌즈 영역(왜곡 상쇄), 같은 거리(배율 상쇄), 절대 좌표 미사용
(캘리브레이션·로봇 절대 오차 상쇄). **원인을 구분할 필요가 없다.** 랙 기울기든, 슬롯
가공 편차든, 로봇 절대 오차든 전부 "둘 사이 어긋남"에 이미 들어 있다.
FT를 차분으로 쓰는 것(§2.2 of plan)과 같은 원리다.

**연속 비주얼 서보잉이 아니라 look-then-move로 한다.**

```
[하지 말 것] 연속 VS: 움직이며 실시간 추종
  → MoveIt Servo, 저지연, 안정성 튜닝, 모션 블러 대응 필요
  → 그런데 목표물(슬롯)은 움직이지 않는다. 얻을 게 없다.

[할 것] look-then-move
  above 포즈 정지 (어차피 웨이포인트)
    → 1프레임 (정지 상태, 다중 프레임 평균 가능)
    → 어긋남 계산 → 상대 이동 → 하강
```
정지 측정이므로 **더 쉽고 더 정확하다.**

**그리퍼가 아니라 퍽을 본다.**

| 무엇을 보나 | 잡히는 오차 |
|---|---|
| 그리퍼 ↔ 슬롯 | 로봇 위치 오차만 |
| **퍽 ↔ 슬롯** | 로봇 위치 오차 **+ 파지 편차** |

퍽을 비뚤게 잡았으면 그리퍼는 제자리인데 퍽이 어긋난다. 정렬 대상은 퍽이다.

**픽셀↔mm 환산은 그 자리에서 직접 잰다 — 캘리브레이션 불필요.**

```
로봇을 X로 +1 mm 조깅 → 퍽이 화면에서 몇 픽셀 이동하는지 측정
→ "1 mm = 12 픽셀"  (그 포즈에서의 환산 계수)
→ 어긋남 36 픽셀이면 3 mm 보정
```
포즈마다 1회 측정해 두면 된다. `T_base_cam` 도, 내부 파라미터도, 왜곡 보정도, 좌표
변환도 거치지 않는다. **오차가 낄 자리가 거의 없다.**

**사이클 타임**: 삽입 지점 4곳(step 3/9/14/20) × 약 0.5 s(촬영 0.1 + 계산 0.01 +
상대 이동 0.4) ≈ 2 s. 다만 이 포즈들은 검사 지점(C1/C3/C5/C7)과 같은 자리이므로
한 프레임이 "슬롯 비었나"와 "얼마나 어긋났나"를 동시에 답한다 → 실제 추가는 더 적다.

**안전장치: 보정량 상한.** 계산된 보정이 한계(예: 5 mm)를 넘으면 보정하지 말고 **정지**.
슬롯을 잘못 짚었거나, 랙이 크게 움직였거나, 검출이 틀린 상황이다. 그대로 보정하면
엉뚱한 곳으로 간다.

### 1.2.3 ⚠ 로봇 팔 가림 — 순수 정면이 아니라 30° 비스듬

그리퍼는 **local Z 방향으로 접근**해서 −50 mm로 후퇴한다. 순수 정면 뷰는 광축이 바로 그
Z 방향이므로 **로봇 팔이 카메라를 향해 정면으로 들어와 슬롯을 가린다.**

```
        랙
        ║
        ║◄── 퍽 (그리퍼가 Z로 접근)
        ║         ↖
        ║           로봇 팔 진입 통로
        ║
     ↙ 30°
  카메라  ← 통로를 비켜난다
```

| | 순수 정면 | **30° 비스듬 (권장)** |
|---|---|---|
| X (측방, 최대 3 mm) | 100 % | **87 %** |
| Z (깊이, 최대 0.45 mm) | 0 % | **50 %** (덤) |
| 로봇 팔 가림 | **심각** | 회피 |

타협이 아니라 개선이다 — X를 13 % 잃고, 가림을 피하고, 못 잡던 Z를 절반 얻는다.

**정확한 각도는 현장에서 정한다. 쉬운 확인법**: 후보 위치에 휴대폰을 두고 사이클을
한 번 돌려서 무엇이 가려지는지 본다. 카메라를 사기 전에 할 수 있다.

### 1.3 가림(occlusion)을 미리 설계한다

카메라가 1대뿐이라 **로봇 팔이 앞을 가리면 아무것도 못 본다.**

- 로봇이 랙에 접근하는 방향과 **다른 쪽**에 카메라를 놓는다.
- 촬영은 팔이 비켜난 포즈(`standby`, `retreat`)에서만 한다. 어차피 검사 시점이 그렇다.
- **가려졌을 때 추측하지 않는다.** 태그가 안 보이거나 ROI가 팔에 덮이면 → `UNKNOWN` →
  정지. "아마 비어 있겠지"가 사고를 만든다.

### 1.4 마운트 강성 — 의외로 가장 흔한 실패 원인

카메라가 **0.1°만 기울어도** 1 m 거리에서 **1.7 mm** 어긋난다. 요구 정밀도가 0.7 mm인데.

- 얇고 긴 폴에 매달지 말 것. **짧고 굵게.**
- **로봇과 같은 테이블(브레드보드)에 직접 고정.** 벽이나 천장은 안 된다 —
  온도와 건물 진동으로 로봇과 따로 움직인다.
- 삼각대 금지. 조인트가 미세하게 흐른다.
- 나사는 풀림방지 처리.

## 2. 두 번째로 중요한 것: 백라이트 (역광) 실루엣

### 2.1 왜 이게 그렇게 좋은가

지금 가장 큰 기술 리스크가 **알루미늄 반사**다. 앞에서 빛을 비추면 금속이 번쩍여서
에지가 사라지고 depth가 뚫린다. 조명을 아무리 잘 잡아도 완전히는 못 없앤다.

**뒤에서 비추면 이 문제가 통째로 사라진다.**

```
   확산 백라이트 패널        퍽/랙            카메라
   ░░░░░░░░░░░░░  ──빛──▶  ██████  ─────▶   ●
   (균일한 흰 면)          (검은 실루엣)

   → 물체는 완전한 검은색, 배경은 완전한 흰색
   → 에지가 극단적으로 선명. 서브픽셀 측정 가능
   → 표면 반사·색·오염·주변 조명 변화 전부 무관
```

산업용 치수 측정은 거의 항상 이 방식을 쓴다. 이유가 있다.

### 2.2 얻는 것

| | 앞에서 조명 | 백라이트 실루엣 |
|---|---|---|
| 금속 반사 | 심각한 문제 | **무관** |
| 주변 조명 변화(형광등, 낮/밤) | 영향 받음 | **무관** |
| 배경 잡음 | 영향 받음 | **무관** |
| 에지 선명도 | 보통 | **극대** |
| 필요한 알고리듬 | 복잡 | **임계값 하나** |
| ML 필요성 | 있을 수도 | **없음** |

`UNKNOWN` 발생률(= ML 투입 여부의 판단 기준)을 가장 확실하게 낮추는 방법이다.

### 2.3 실무 주의

- **확산(diffuse) 패널**을 쓴다. LED 점광원을 그냥 두면 안 된다. 얇은 LED 패널 + 유산지/
  아크릴 확산판.
- **⚠ 퍽과 그리퍼가 한 덩어리로 붙어 보일 수 있다.** 상대 측정(§1.2.2)은 퍽의 윤곽을
  그리퍼와 분리해서 봐야 한다. 퍽 원반이 손가락 바깥으로 충분히 튀어나오는지 실물 확인
  필요. 안 되면 (a) 백라이트를 슬롯 영역에만 국한하고 퍽 영역은 전면 조명, 또는
  (b) 노출을 달리한 2프레임을 번갈아 찍는다.
- 랙 뒤 공간이 필요하다. 사진상 랙 뒤는 파티션이라 **얇은 패널이면 가능해 보이지만
  실측 확인 필요** (§6-1).
- 밝기는 **고정**. 조광 가능한 제품이면 다이얼을 고정하고 표시해 둔다.
- 카메라 노출을 백라이트에 맞춰 고정하면 주변 조명은 아예 무시된다.
- **태그는 백라이트로 못 읽는다** (검은 실루엣이 되어버림). 태그는 카메라 쪽에서 조명받는
  면에 붙이고, 실루엣 측정 영역과 분리한다. 필요하면 태그 검출용 프레임과 실루엣 측정용
  프레임을 **노출 다르게 번갈아 찍는다** (같은 카메라로 2장, 0.1초).

## 3. AprilTag를 잘 쓰는 법

### 3.1 왜 AprilTag가 ArUco보다 나은가 (좋은 선택입니다)

- **오검출(false positive)이 훨씬 적다.** tag36h11은 해밍 거리가 커서 잘못 읽을 확률이
  극히 낮다. 지그 위치를 잘못 커밋하면 충돌이므로, 이 특성이 안전에 직결된다.
- 비스듬한 각도, 부분 가림, 낮은 조도에서 검출률이 높다.
- 검출 속도는 ArUco보다 느리지만, 카메라 1대 / 수 Hz면 전혀 문제 안 된다.

**단, 자세(회전) 정밀도 문제는 AprilTag도 똑같다.** 평면 태그 하나의 PnP는 원리적으로
면외 회전이 부정확하고, 자세가 뒤집혀 보이는 경우(ambiguity)가 있다. 태그를 바꾼다고
해결되지 않는다 — §3.3의 배치로 해결한다.

### 3.2 즉시 바꾸면 되는 설정 3개 (공짜)

**① `quad_decimate = 1.0`**
기본값이 보통 2.0인데, 이건 이미지를 절반으로 줄여서 검출한다. 속도는 빨라지지만
**정밀도가 그만큼 날아간다.** 정밀 측정에는 반드시 1.0.
→ 가장 흔하고 가장 아까운 정밀도 손실.

**② 노출 고정 (auto-exposure OFF)**
자동 노출은 프레임마다 밝기가 바뀌고, 밝기가 바뀌면 에지 검출 위치가 미세하게 흔들린다.
→ 노출·게인·화이트밸런스 **전부 수동 고정.** 오토포커스 렌즈면 초점도 고정.
→ 이거 하나로 재현성이 눈에 띄게 좋아진다.

**③ `refine_edges = true`**
서브픽셀 에지 정제. 켜 둔다. 비용 거의 없다.

### 3.3 태그 배치 3개 원칙

**① 크게** — 이미지에서 태그 한 변이 **최소 100 픽셀** 이상 되게. 작으면 정밀도가 급격히
나빠진다. 작은 태그 여러 개보다 큰 태그 하나가 낫다.

**② 멀리 떨어뜨려서** — 자세(회전) 정확도는 태그 사이 거리에 반비례해서 좋아진다.

```
   [나쁨] 모아 붙임              [좋음] 멀리 배치

   ┌────────┐                  ┌────────┐
   │ ▣▣▣    │                  │ ▣      │  ← 위
   │        │                  │        │
   │        │                  │        │
   │        │                  │   ▣   ▣│  ← 아래 양쪽
   └────────┘                  └────────┘

   baseline 짧음 → 각도 오차 큼    baseline 김 → 각도 오차 작음
```
랙 위·아래 끝에 하나씩, 그리고 하나 더. **세 점이 일직선이 되지 않게.**

**③ 측정 대상과 같은 평면에** — 태그 면과 슬롯 기준면이 다르면 그 사이 변환을 따로
알아야 하고, 그게 새로운 오차원이 된다. 지그의 **가공된 기준면**에 붙인다.

### 3.4 여러 태그를 "묶어서" 푼다 (tag bundle)

태그마다 포즈를 따로 구해서 평균내면 안 된다. **모든 태그의 코너를 한 번에 PnP에 넣는다.**
"이 태그들은 서로 이만큼 떨어진 하나의 강체"라는 정보를 쓰는 것이고, 이게 §3.3-②의
baseline 효과를 실제로 얻는 방법이다.

`apriltag_ros`에 **tag bundle** 기능이 이걸 위해 있다. standalone tag 대신 bundle로 설정.
번들 정의에는 태그 간 상대 위치를 mm 단위로 정확히 적어야 하므로, **태그를 판에 붙일 때
치구를 쓰거나 판 자체에 각인**하는 게 좋다.

### 3.5 태그 크기 — 여기서 틀리면 모든 거리가 비례해서 틀린다

- 설정에 넣는 크기는 **의도한 값이 아니라 캘리퍼로 실측한 값.**
  프린터는 100%로 설정해도 1~2% 어긋난다. 1% 오차 = 1 m 거리에서 10 mm 오차.
- **크기의 정의를 문서에서 확인할 것.** 도구마다 "검은 테두리 바깥 변"인지 "데이터
  영역 변"인지 다르다. 여기서 헷갈리면 수 % 오차가 조용히 들어간다.
- **종이 금지.** 습기·마모로 서서히 변형되는데, 정밀도가 조용히 나빠져서 알아채기 어렵다.
  → **알루미늄 각인 / 아노다이징 마킹** 권장. 재설치가 잦으면 더욱.

### 3.6 흔한 검출 실패

- **흰 여백 부족** — AprilTag는 검은 테두리 바깥에 최소 1비트 폭의 흰 여백이 필요하다.
  딱 맞춰 자르면 검출이 안 된다.
- **광택 표면** — 무광으로. 코팅된 알루미늄이 번쩍이면 태그가 안 읽힌다.
- **모션 블러** — 고정 카메라 + 정지 촬영이면 무관. 노출 시간만 너무 길지 않게.
- **태그가 너무 작음** — §3.3-① 참조.

## 4. 카메라와 렌즈

### 4.1 필요한 분해능을 먼저 계산한다 (간단함)

```
mm/픽셀 = 시야 크기(mm) ÷ 픽셀 수
측정 분해능 ≈ (mm/픽셀) ÷ 5     ← 좋은 에지에서 서브픽셀 1/5 픽셀 가정
```

예: 랙 높이 400 mm를 세로 1200 픽셀로 본다면

```
400 ÷ 1200 = 0.33 mm/픽셀
0.33 ÷ 5   = 0.07 mm  → 판정 기준 0.7 mm 대비 10배 여유. 충분.
```

640×480 웹캠이면: `400 ÷ 480 = 0.83 mm/px` → `0.17 mm`. 여유 4배 — 아슬아슬하다.

**목표: 판정 임계값(dz_max) 대비 분해능 여유 5배 이상.**
시야를 랙만으로 좁힐수록 좋아진다. 필요 없는 배경을 화면에 담지 않는다.

### 4.2 고를 때

| 항목 | 권장 | 이유 |
|---|---|---|
| 셔터 | **글로벌 셔터** | 롤링 셔터는 진동에 왜곡 |
| 해상도 | **1920×1200 (2.3 MP) 이상** | §4.1 계산 결과 충족 |
| 센서 | **모노크롬** (컬러보다 유리) | 베이어 보간이 없어 에지가 선명, 감도 2배. 치수 측정은 모노가 정석 |
| 렌즈 | **고정 초점거리, 저왜곡** | 바리포컬/줌 금지 — 재현성이 없다 |
| 인터페이스 | USB3 또는 GigE | |

컬러가 꼭 필요한 이유가 없으면 모노를 쓴다. 실루엣 측정에는 색이 아무 의미 없다.

### 4.3 내부 파라미터 캘리브레이션은 제대로

태그 포즈 정확도의 **상한**을 여기서 결정한다. 대충 하면 뒤에서 뭘 해도 안 올라간다.

- ChArUco 보드로 **20~30장**. (내부 캘리브레이션에는 ChArUco가 여전히 좋다 —
  지그 로컬라이제이션에 AprilTag를 쓰는 것과 별개 얘기다.)
- **화면 구석까지 골고루.** 가운데만 찍으면 왜곡 계수가 안 나온다.
- 보드를 기울여서도 찍는다.
- 왜곡 계수까지 추정한다.
- 재투영 오차(reprojection error) **0.3 픽셀 이하** 목표. 넘으면 다시.

### 4.4 켜고 나서 20분 기다린다

센서가 데워지면서 초점과 기하가 미세하게 변한다. **전원 켜고 10~20분 후에**
캘리브레이션하고, 운영 중에도 아침 첫 사이클 전에 예열한다.

## 5. 안정성 — 시간이 지나도 안 틀어지게

성능은 처음 한 번 잘 맞추면 되지만, 안정성은 **틀어졌다는 걸 스스로 알아채는 구조**를
만드는 문제다.

### 5.0 헷갈리기 쉬움: "캘리브레이션(1회)"과 "측정(매번)"은 다른 것

카메라가 하는 일은 두 가지이고, 주기가 다르다.

```
[매번]  측정:        T_cam_rack    "랙은 카메라에서 왼쪽 30cm, 앞 50cm"
                                    ↑ 카메라 말이라 로봇이 못 알아들음
[1회]   캘리브레이션: T_base_cam    "카메라는 로봇에서 이 위치, 이 방향"
                                    ↑ 번역 규칙
[결과]              T_base_rack = T_base_cam · T_cam_rack
                                    ↑ 로봇이 실제로 갈 수 있는 좌표
```

자에 비유하면 **눈금을 새기는 건 한 번**(캘리브레이션), **그 자로 재는 건 잴 때마다**
(측정). 눈금 없는 자로는 매번 재도 숫자가 안 나온다.

| 무엇 | 주기 | 이유 |
|---|---|---|
| `T_base_cam` (번역 규칙) | **평생 1회** | 카메라와 로봇이 같은 브레드보드에 고정 → 안 변함 |
| `T_cam_rack` (지그 위치) | **재설치마다** (최소), 권장은 **매 사이클** | 지그가 움직이니까 |
| 슬롯별 미세 보정 | **매 사이클** | 잔여 오차 흡수 (`vision_inspection_plan.md` §4.3) |

**매 사이클 갱신을 권한다.** 어차피 태그가 화면에 있으니 비용이 거의 없고, "누가 랙을
툭 쳤다"를 즉시 잡아낸다. 단 안전장치가 필요하다:

- **작은 변화**(노이즈 수준) → 평활화해서 반영
- **큰 변화**(예: 5 mm 이상) → 반영하지 말고 **정지 + 운영자 확인**.
  태그 오검출로 잘못된 위치를 그대로 믿으면 다음 동작이 충돌이다.

### 5.0.1 캘리브레이션은 "로봇 위치를 알기 위해서"가 아니다

자주 하는 오해다. **로봇은 자기 팔이 어디 있는지 이미 안다** — 관절 엔코더 + 순기구학
(TF `base_link → tool0`). 반복정밀도 ±0.03 mm로, 카메라로 재는 것보다 훨씬 정확하다.

카메라가 필요한 이유는 **로봇이 못 느끼는 것**(랙, 측정 홀더 — 엔코더가 없다)의 위치를
알기 위해서다. 캘리브레이션은 그 정보를 **카메라 좌표 → 로봇 좌표로 옮기는 번역기**다.

캘리브레이션 절차(그리퍼에 태그 붙이고 로봇을 움직이며 관측)가 로봇을 측정하는 것처럼
보이지만 반대다 — **로봇이 자기 위치를 정확히 알기 때문에 그것을 기준자로 삼아** 카메라를
로봇 좌표계에 정렬시키는 것이다.

### 5.0.2 카메라↔로봇 캘리브레이션은 1회면 끝난다

**eye-in-hand(손목 카메라용)는 안 해도 된다** — 손목에 카메라가 없으니까.
**하지만 `T_base_cam`(카메라↔로봇 베이스)은 반드시 필요하다.** 카메라가 "랙이 여기 있다"고
말해도, 그게 로봇 좌표로 어디인지 모르면 로봇이 못 간다.

```
T_base_rack = T_base_cam · T_cam_rack
              ▲
              └── 이게 없으면 아무것도 안 됨
```

이건 eye-in-hand가 아니라 **eye-to-hand** 캘리브레이션이다. 그리고 **카메라를 로봇과 같은
브레드보드에 고정하면(§1.4) 평생 1회로 끝난다:**

| 상황 | 재캘리브레이션 |
|---|---|
| 랙만 재설치 | **불필요** |
| 셀 전체 이사 (로봇+카메라 함께) | **불필요** |
| 카메라·렌즈·초점을 건드림 | 필요 |
| 로봇을 브레드보드에서 분리 | 필요 |

§1.4에서 마운트를 테이블 직결로 권한 이유가 진동 때문만이 아니다.
**캘리브레이션 수명** 때문이다.

절차는 간단하다 — 태그를 그리퍼에 붙이고, 로봇을 10~20 자세로 움직이며 관측하고,
`cv2.calibrateHandEye`. 로봇 기구학이 자 역할을 하므로 별도 측정 도구가 필요 없다.
기존 `hand_eye_calibration_node.py` 의 `invert_gripper2base: true` 가 이 변환을 이미
지원한다. 상세는 `vision_inspection_plan.md` §4.1 (M3).

**놓치기 쉬운 두 가지:**
- **자세의 회전을 충분히 다양하게.** 위치만 옮기고 방향을 안 바꾸면 해가 불안정해진다.
- **내부 파라미터를 먼저 실측할 것.** 기존 노드는 D405 값이 하드코딩돼 있고
  `dist_coeffs = zeros(5)` 다. 새 카메라에는 틀리다 (§4.3).

### 5.1 자기 검증 태그 — 가장 쉽고 가장 효과적

**여분 태그 하나를 로봇 베이스에 영구 부착한다.**
매 측정마다 그 태그까지의 거리·각도를 계산해서 저장된 기준값과 비교한다.

브레드보드 임의 위치가 아니라 **로봇 베이스**에 붙이는 이유: §5.0의 `T_base_cam` 이
1회 캘리브레이션으로 고정되므로, 그 관계가 유지되는지를 직접 감시해야 한다.
지키고 싶은 관계를 정확히 겨냥하는 것이다.

```
매일 아침 자동 체크:
  기준 태그 포즈 측정 → 저장값과 비교
    차이 < 0.3 mm  → 정상
    차이 ≥ 0.3 mm  → "카메라가 움직였습니다" 경고 → 재캘리브레이션
```

카메라 마운트가 밀렸는지, 나사가 풀렸는지, 온도로 흘렀는지를 **사람이 알아채기 전에**
잡아낸다. 태그 하나 붙이고 비교 코드 몇 줄이면 끝난다.

### 5.2 상시 기록할 지표 4개

이 값들을 PV로 내보내고 추세를 본다. **값 자체보다 추세가 중요하다.**

| 지표 | 나빠지면 의미하는 것 |
|---|---|
| 태그 포즈의 프레임 간 표준편차 | 진동, 조명 흔들림, 노출 문제 |
| 태그 검출 실패율 | 태그 오염/손상, 조명 변화, 가림 |
| 기준 태그 오차 (§5.1) | 카메라 마운트 이동 |
| 정상 안착 Δz 분포의 평균 | 기구 마모, 지그 변형 |

마지막 항목이 특히 유용하다 — **고장 나기 전에** 기구 문제를 알려준다.

### 5.3 여러 프레임 평균

재설치 캘리브레이션은 어차피 로봇이 멈춰 있을 때 한다. **10~30 프레임 평균**을 쓴다.
랜덤 노이즈가 √N배로 줄어든다 (25장이면 1/5). 시간은 1초도 안 걸리고 공짜다.

단, **평균 전에 이상치를 버린다.** 태그가 한 프레임에서 잘못 뒤집혀 검출되면 평균이
오염된다. 중앙값(median) 또는 이상치 제거 후 평균.

| 주기 | 항목 |
|---|---|
| 매일 (자동) | 기준 태그 검증 (§5.1) |
| 재설치 시 | 지그 로컬라이제이션 3회 반복 → σ 확인 → 운영자 승인 |
| 월 1회 | 태그 오염/손상 육안 점검, 렌즈 청소, 마운트 나사 확인 |
| 6개월 | 내부 파라미터 재캘리브레이션 |

## 6. 남는 문제와 대안

### 6.1 카메라 1대로 안착 판정이 되는가

**정면 뷰 + 백라이트(§1.2, §2)가 되면 — 된다.** 안착 높이(Y)와 기울기, 측방 오프셋(X)이
전부 이미지 평면 안의 측정이 되므로 오히려 유리하다.

**정면 배치나 백라이트가 물리적으로 불가능하면 — 어렵다.** 그 경우 대안:

1. **손목 D405를 병용한다** (권장 대안). 이미 있고, hand-eye 캘리브레이션 인프라도 있다.
   역할 분담이 깔끔하다:
   - **외부 고정 카메라**: 지그 로컬라이제이션(AprilTag), 10슬롯 재고, 점유 판정
   - **손목 D405**: 안착 근접 검사 (Δz, 기울기)

   "외부 1대"라는 결정과 충돌하지 않는다 — 새로 사는 카메라가 1대일 뿐, 이미 있는
   D405를 놀리는 게 오히려 손해다.

2. **접촉식 확인** — 안착 후 그리퍼를 살짝 내려 퍽 상단에 닿는 높이를 FT로 잰다.
   비전 없이 Δz를 직접 측정하는 방법. 사이클 타임이 늘고 퍽에 접촉하지만 확실하다.

3. **측정 홀더에 근접 센서** — 광전/정전용량 센서 하나로 "완전히 안착됨"을 판정.
   측정 홀더는 1개뿐이라 비용이 작다. 랙 10슬롯은 비용이 커서 안 맞는다.

### 6.2 카메라 1대 배치로 랙과 측정 홀더를 동시에 볼 수 있는가

사진상 랙과 측정 홀더가 떨어져 있다. 한 화면에 둘 다 담으면 **시야가 넓어져서 mm/픽셀이
나빠진다** (§4.1). 선택지:

- **랙 위주로 배치**하고 측정 홀더는 손목 카메라 담당 (6.1-1과 같은 결론)
- 광각으로 둘 다 담되 분해능 여유를 §4.1로 계산해서 확인. 여유 5배 안 나오면 포기.

→ **§6-1의 실측 확인 후 결정.**

## 8. 확인 필요 (실측해야 결정되는 것)

1. **로봇 팔 가림 각도** — §1.2.3. 후보 위치에 휴대폰을 두고 사이클을 한 번 돌려
   무엇이 가려지는지 확인한다. **카메라 구매 전에 할 수 있다. 최우선.**
2. **랙 뒤에 백라이트 패널을 넣을 공간이 있는가** — 사진상 파티션까지의 거리.
3. **퍽 실루엣이 그리퍼와 분리되는가** — §2.3. 상대 측정(§1.2.2)의 전제 조건.
4. **`above` 포즈에서 퍽과 목표 슬롯이 한 프레임에 들어오는가** — 5 mm 간격이므로
   거의 확실하지만, 시야 범위와 함께 확인.
3. **랙과 측정 홀더를 한 화면에 담을 때의 시야 크기** — §4.1 계산 입력.
4. **로봇 팔이 랙을 가리는 포즈 범위** — 촬영 시점 결정 입력.
5. `apriltag_ros`의 ROS2 Humble 패키지 가용성과 tag bundle 설정 형식 — 로봇 PC에서 확인.
6. 태그 크기 정의(검은 테두리 바깥 변 vs 데이터 영역) — 쓰는 패키지 문서에서 확인.
