# 퍽 장착 검증 + 마커 기반 지그 로컬라이제이션 개발 계획

대상: UR3e + Hand-E 시료 교환기 (시료 랙 10슬롯 + 측정 홀더 1개)

**Rev 2** — 잦은 재설치 대응(마커 기반 캘리브레이션)과 그립 상태 머신을 반영.

해결하려는 문제:
1. **측정 홀더에 퍽이 이미 있는데 또 넣으려고 함** → 퍽끼리 충돌, protective stop
2. **퍽이 제대로 장착되지 않음** → 기울어짐 / 덜 들어감 / 그리퍼 후퇴 시 낙하
3. **헛파지** — 퍽을 못 잡은 채로 시퀀스가 계속 진행
4. **설치 위치가 계속 바뀜** → 재설치마다 10슬롯 재티칭이 필요한 현재 구조

---

## 0. 요약 — 결론 먼저

### 0.1 머신러닝은 필요 없다 (그리고 재설치가 잦다는 사실이 그 결론을 더 강화한다)

이 문제는 인식(recognition) 문제가 아니라 **측정(metrology) 문제**다. 퍽 형상이 하나로
고정돼 있고, 지그가 강체이며, 판정 기준을 mm/deg로 기술할 수 있다.

**재설치가 잦다는 조건은 ML에게 불리하고 기하 방식에게 유리하다** — 직관과 반대다:

| | 재설치 시 발생하는 일 | 복구 비용 |
|---|---|---|
| **ML** | 시점·배경·조명이 전부 바뀜 → 학습 분포 이탈 → 성능이 조용히 저하됨 (경고 없이) | 재수집 + 재학습 + 재검증, **재설치마다** |
| **기하 + 마커** | ROI와 기준 평면이 지그 프레임에 매달려 있으므로 자동으로 따라감. 판정량(Δz, θ)이 **지그 상대량**이라 설치 불변 | 마커 스캔 1회 (~1분) |

ML이 "환경 변화에 유연하다"는 통념은 **학습 분포 안에서의 변화**에 해당한다. 카메라가
통째로 다른 위치로 가는 것은 분포 밖 변화이고, ML은 여기서 가장 나쁘게 실패한다 —
틀렸다는 사실을 스스로 알리지 못한 채 틀린다.

ML의 유일한 잔여 니치는 **금속 반사로 인한 depth 드롭아웃**이고, 이건 Phase 0의 조명 개선으로
먼저 친다. 그래도 `UNKNOWN` 비율이 2%를 넘으면 그때 **정상 데이터만 쓰는 이상탐지**를 보조로
넣는다 (§3 참조). 지도학습 분류기는 끝까지 안 쓴다.

### 0.2 이미 시스템 안에 있는데 버려지고 있는 신호 3개

조사 결과, 필요한 신호의 상당수가 **이미 하드웨어에서 읽혀 소프트웨어까지 도달했다가
버려지고 있다.** 새로 만들 것이 아니라 배선만 하면 된다.

| 신호 | 현재 상태 | 근거 |
|---|---|---|
| **`gOBJ` (물체 검출)** | Hand-E가 하드웨어로 판정해서 Modbus로 보내고, 드라이버가 파싱까지 하는데 **ROS로 export 안 함** | `protocol_logic.hpp:56` 에 `ObjectDetectionStatus` 열거형 정의, `hande_hardware_interface.cpp:151` `export_state_interfaces()` 는 POSITION/VELOCITY만 내보냄 |
| **그리퍼 전류 (0–2.55 A)** | 동일하게 파싱만 하고 export 안 함 | `hande_gripper.hpp:139` `get_current()` |
| **손목 6축 힘/토크** | 컨트롤러가 `ft_data` 토픽으로 publish 중, **아무도 구독 안 함** | `ur_hande_controllers.yaml:74-86` (frame `tool0`) |
| 그리퍼 스트로크 연속값 | `/joint_states` 로 들어오는데 시퀀스가 **이진 open/close로 축약하고 버림** | `epics_triggered_sequence.cpp:1371` |

특히 **`gOBJ`가 결정적이다.** Robotiq 프로토콜의 `REQ_POS_NO_OBJECT`(=3)는
"요청 위치까지 다 닫혔는데 아무것도 안 걸렸다" = **헛파지 그 자체**를 하드웨어가 알려주는
값이다. `export_state_interfaces()` 에 두 줄 추가하면 얻는다.

### 0.3 재설치 대응의 진짜 병목은 마커가 아니라 웨이포인트 저장 형식이다

`taught_waypoints.yaml` 은 **관절각 절대값**을 저장한다:

```yaml
holder1_standby:     [7개 관절값]
holder1_on_position: [7개 관절값]
sample_holder_on_position: [7개 관절값]
holder_multi_x_offsets: [0.0003, 0.0005, 0.0015, 0.0015, 0.003, 0.003, 0.003, 0.003, 0.003]
holder_multi_z_offsets: [0.0, 0.0, 0.0, 0.0002, 0.00025, 0.0003, 0.00035, 0.0004, 0.00045]
```

지그가 1 mm라도 움직이면 이 값들이 전부 무효다. 마커를 붙여서 `T_base_rack`을 알아내도,
웨이포인트가 관절 절대값인 한 **그 정보를 쓸 곳이 없다.**

추가로, 위의 18개 오프셋 배열은 홀더 번호에 따라 **단조 증가**한다. 이건 랙의 기울기 또는
직각도 오차가 슬롯을 따라 누적되는 것을 슬롯마다 손으로 보정한 흔적이다. 지그 자세를
6-DoF로 한 번 피팅하면 이 18개가 **자세 파라미터 하나로 흡수된다.**

따라서 재설치 대응의 핵심 작업은 **관절 절대 티칭 → 지그 프레임 상대 포즈 + 런타임 IK**
리팩터다 (§5). 마커는 그 입력을 공급하는 수단이다.

## 2. 그립 상태 머신 (비전 불필요, 최우선)

### 2.1 신호 결합

`gOBJ` 하나로는 부족하다. `gOBJ`는 "뭔가에 걸려서 멈췄다"를 말할 뿐, **"올바른 것에
걸렸다"** 를 말하지 않는다. 퍽을 비스듬히 물었거나 이물을 물어도 `gOBJ=2`가 나온다.
스트로크가 **치수**를 알려주므로 둘을 결합한다.

```
Robot:GraspState (mbbi)
  0 UNKNOWN    초기 / 그리퍼 통신 불가
  1 OPEN       열림 완료, 물체 없음
  2 EMPTY      닫힘 완료, 물체 미검출              ← 헛파지 (F2)
  3 HOLDING    닫힘 중 접촉 정지 + 스트로크 정상    ← 정상 파지
  4 MISGRIP    물체 검출됐으나 스트로크 이상        ← 비스듬히 물림 / 이물
  5 DROPPED    HOLDING → 스트로크 완전 폐쇄로 붕괴  ← 이송 중 낙하 (F3)
  6 FAULT      그리퍼 fault (gFLT)
```

판정 규칙:
```
gOBJ == REQ_POS_NO_OBJECT (3)                      → EMPTY
gOBJ == STOPPED_CLOSING_DETECTED (2)
    AND |stroke − stroke_puck| ≤ tol                → HOLDING
    AND 그 외                                        → MISGRIP
HOLDING 유지 중 stroke → stroke_closed 로 붕괴       → DROPPED
gFLT != 0                                          → FAULT
```

`stroke_puck` 은 퍽 파지 직경에서 결정된다 — **§9의 미확인 사항 1번이 확정돼야 값이 정해진다.**

### 2.2 보조 확증 (선택, 정확도 향상용)

- **그리퍼 전류 (`gCU`)**: 정상 파지 시 유지 전류가 안정적. 한계 파지는 전류가 떨어진다.
- **FT 차분**: 같은 포즈에서 파지 전/후 `ft_data`의 Δ|F| ≈ 퍽 무게.
  **반드시 차분으로 쓴다** — UR 내장 FT의 절대 정확도는 낮지만, 동일 포즈 차분은
  중력·툴하중·바이어스가 상쇄되어 분해능 한계까지 쓸 수 있다.
  (구체적 수치 한계는 UR3e 데이터시트로 확인 필요 — §9)

### 2.3 DROPPED는 체크포인트가 아니라 상시 감시

낙하는 언제든 일어난다. `HOLDING` 상태인 동안 ~10 Hz로 스트로크를 감시하는 백그라운드
모니터가 필요하다. 스텝 경계에서만 확인하면 낙하 후 여러 스텝을 헛돌게 된다.

### 2.4 필요한 코드 변경

1. `hande_hardware_interface.cpp:151` `export_state_interfaces()` 에
   `object_detection` / `current` 상태 인터페이스 추가 (드라이버가 이미 값을 갖고 있음)
2. 두 값을 publish 하는 broadcaster 추가 (또는 기존 그리퍼 상태 토픽 확장)
3. 그립 상태 머신 노드 → `Robot:GraspState`, `Robot:GripperPos`, `Robot:GripperCurrent`
4. 시퀀스에서 step 4/15 직후 `GraspState == HOLDING` 확인, 아니면 정지

**업스트림 영향**: `robotiq_hande_driver`는 외부 패키지다. 포크 수정 시 업스트림 diff를
최소로 유지하고, 변경 내역을 `doc/` 에 기록한다 (향후 업스트림 갱신 시 재적용해야 함).

## 3. 알고리듬 vs 머신러닝 (Rev 1에서 유지, 재설치 조건 반영)

### 3.1 점유 판정 (F1/F4/F6/F7)

판별 마진이 퍽 두께(수 mm~cm)라 SNR이 압도적. ROI depth median 하나로 결정된다.
필요 데이터는 빈/찬 상태 각 10~20 프레임. ML은 수백~수천 장을 쓰고 동등 이하 성능.
→ **논쟁 여지 없이 알고리듬.**

### 3.2 안착 품질 (F5/F8)

마진이 0.5~3 mm / 1~5°. 여기가 실제 판단 지점이다.

| 항목 | 기하 (평면 피팅) | 지도학습 CNN | 이상탐지 (one-class) |
|---|---|---|---|
| **실패 데이터 필요** | **불필요** | **필수 (200+)** | **불필요** |
| 정상 데이터 필요 | 10~30 프레임 | 500+ | 100~300 |
| 미학습 실패 모드 | **검출됨** (open-set) | **놓침** (closed-set) | 대체로 검출 |
| **재설치 후** | **자동 추종** (지그 프레임 상대) | **재수집·재학습** | 정상셋 재구축 |
| 출력 | Δz [mm], θ [deg] | 확률 | 이상 점수 + 히트맵 |
| 임계값 근거 | **기계 공차에서 유도** | 검증셋 튜닝 | 검증셋 튜닝 |
| 반사 강건성 | **낮음** | 높음 | 중간 |
| 개발 기간 | 3~4주 | 6~10주 + 수집기간 | 3~5주 |

지도학습을 배제하는 결정적 이유 두 가지:

1. **실패 데이터가 희소한 게 문제의 본질이다.** 가끔 일어나니까 문제인 것이다.
   200장을 모으려면 고의로 200번 잘못 꽂아야 하고, 고의 실패는 실제 실패와 분포가 다르다.
2. **안전 인터록에 closed-set 분류기를 쓰면 안 된다.** 학습에 없던 실패 모드는 높은 확률로
   "정상"으로 분류된다. 인터록의 요구사항은 "본 적 있는 불량을 잘 맞히기"가 아니라
   **"정상 아닌 것을 통과시키지 않기"** 다.

여기에 재설치 조건이 3번째 이유를 추가한다: **재설치마다 재학습은 운영 불가능하다.**

### 3.3 권고 구조

```
Layer 0  gOBJ + 스트로크 + 전류 + FT   → F2, F3, F9    (비용 ~0, 이미 배선됨)
Layer 1  마커 + depth 지그 로컬라이제이션 → F10          (재설치 대응의 기반)
Layer 2  기하/깊이 점유 판정             → F1,F4,F6,F7
Layer 3  기하/깊이 안착 판정             → F5, F8       (주력)
Layer 4  이상탐지 ML (조건부)            → Layer 3의 UNKNOWN·gray zone만
```

Layer 4는 **fail-safe 방향으로만** 작동한다:
- `OK` → `NG` 뒤집기 **가능** (더 보수적으로)
- `UNKNOWN` → `OK`/`NG` 해소 **가능**
- `NG` → `OK` 덮어쓰기 **불가능** — 런타임 `if`가 아니라 타입/API로 강제

## 4. 마커 기반 지그 로컬라이제이션

**확정 사항 (Rev 3): 외부 고정 카메라 1대 + AprilTag(tag36h11)를 쓴다.**
실무 설정·튜닝은 별도 문서 `doc/vision_camera_setup.md` 참조. 이 절은 구조만 다룬다.

### 4.1 세 종류의 마커를 구분한다 (혼동하면 안 됨)

기존 `hand_eye_calibration_node.py`는 **ArUco DICT_6X6_250 + solvePnP + `cv2.calibrateHandEye`**
로 eye-in-hand 캘리브레이션을 한다. 이건 세 용도 중 하나일 뿐이고, 아래 M1에만 해당한다.
M2/M3는 AprilTag로 새로 만든다 (기존 ArUco 코드를 고치는 것이 아니라 별도 경로).

| # | 역할 | 마커 위치 | 산출물 | 재실행 시점 |
|---|------|-----------|--------|-------------|
| **M1** | Eye-in-hand (**기존 구현**) | 고정된 정지 마커 (ID 0) | `T_tool0_cam` | **손목 D405를 병용할 때만 필요.** 외부 카메라만 쓰면 **불필요** |
| **M2** | 지그 로컬라이제이션 (**신규**) | 랙에 3개 이상, 측정 홀더에 2개. **영구 부착** | `T_cam_rack`, `T_cam_measholder` | **재설치마다 (자동)** |
| **M3** | **Eye-to-hand 캘리브레이션 (신규, 필수 1회)** | 태그를 **그리퍼에** 임시 부착 | `T_base_cam` | **평생 1회.** 카메라를 물리적으로 건드렸을 때만 |
| **M4** | **자기 검증 (신규)** | **로봇 베이스에 영구 부착** | 드리프트 감지 | 매 측정 (자동) |

**M1(eye-in-hand)은 외부 카메라만 쓰면 불필요하다.** 손목에 카메라가 없으므로.
`§6.1`의 대안(손목 D405 병용)을 택할 때만 되살린다 — 이미 구현돼 있으니 재사용.

**하지만 카메라↔로봇 관계(`T_base_cam`)는 반드시 필요하다.** 카메라가 `T_cam_rack`을
알아내도 로봇 좌표로 옮기지 못하면 쓸 수 없다:

```
T_base_rack = T_base_cam · T_cam_rack
              ▲
              └── 이게 M3. 없으면 아무것도 안 됨
```

이건 eye-in-hand가 아니라 **eye-to-hand(eye-on-base)** 캘리브레이션이다. 이름이 비슷해
혼동하기 쉽지만 다른 것이다.

**핵심: `T_base_cam`은 평생 1회로 끝난다 — 카메라를 로봇과 같은 강체에 고정하는 조건에서.**

| 상황 | `T_base_cam` 변하나 | 재캘리브레이션 |
|---|---|---|
| 랙만 재설치 | 아니오 | **불필요** |
| 셀 전체를 다른 곳으로 이사 (로봇+카메라 함께) | 아니오 | **불필요** |
| 카메라 마운트를 건드림 / 렌즈·초점 변경 | 예 | 필요 |
| 로봇을 브레드보드에서 분리 | 예 | 필요 |

이것이 `vision_camera_setup.md` §1.4에서 카메라를 **벽·천장이 아니라 로봇과 같은
브레드보드에 직결**하라고 한 진짜 이유다. 진동 때문만이 아니라 **캘리브레이션 수명**
때문이다. 재설치가 아무리 잦아도 M3는 다시 하지 않는다.

**M3 절차 (기존 코드 재사용):**
```
1. 태그를 그리퍼에 붙인다 (임시)
2. 로봇을 10~20개 자세로 움직인다 — 위치뿐 아니라 회전도 충분히 다양하게
   (회전 다양성이 부족하면 calibrateHandEye 해가 불안정해진다)
3. 각 자세에서 카메라로 태그 관측 + /joint_states 기록
4. cv2.calibrateHandEye → T_base_cam
```
`hand_eye_calibration_node.py:463-467` 의 `invert_gripper2base: true` 가 정확히 이
역변환을 수행한다. **파라미터 전환 + 태그를 그리퍼에 부착 + 결과를 `T_base_cam` 으로
해석해 저장**하면 되고, 새 코드는 거의 필요 없다. 로봇 자신의 기구학이 자 역할을 하므로
외부 측정 도구가 필요 없다.

이 1회 작업에는 **AprilTag 포팅이 불필요하다** — 기존 ArUco 경로를 그대로 쓴다.
AprilTag는 매 사이클 읽는 M2/M4 지그 태그용이다.

**⚠ 기존 코드의 함정**: `hand_eye_calibration_node.py:80-85` 는 카메라 내부 파라미터가
**D405 값으로 하드코딩**돼 있고 `dist_coeffs = zeros(5)` 다 ("RealSense는 왜곡 보정된
이미지를 제공"이라는 주석). **새 외부 카메라에는 이게 틀리다.** 일반 산업용 카메라+렌즈는
실제 왜곡이 있고, 0으로 두면 화면 가장자리에서 수 mm 어긋난다. 새 카메라의 내부
파라미터를 실측해서 넣어야 한다 (`vision_camera_setup.md` §4.3).

**M4(로봇 베이스 태그)의 역할이 바뀐다.** 원래 계획에서는 `T_base_cam` 을 매번 구하는
필수 수단이었지만, M3가 1회로 끝나므로 **검증 장치**가 된다. 로봇 베이스에 영구
부착하고, 매 측정마다 `T_cam_M4` 를 저장값과 비교해 **카메라와 로봇의 관계가 틀어졌는지**
직접 감지한다. `vision_camera_setup.md` §5.1의 자기 검증 태그와 **같은 태그 하나로
통합**한다 — 브레드보드 임의 위치보다 로봇 베이스가 낫다. 지키고 싶은 관계를 정확히
감시하기 때문이다.

### 4.2 단일 평면 태그로는 자세 정밀도가 안 나온다 (AprilTag도 동일)

AprilTag는 ArUco보다 **오검출률이 훨씬 낮고 검출이 안정적**이다 (tag36h11 기준). 이건 확실한
개선이다. 하지만 **평면 태그 하나의 PnP는 면외 회전(out-of-plane rotation) 추정이
부정확**하고 자세 뒤집힘(pose ambiguity)이 생기는 문제는 AprilTag도 똑같다. 이건 태그
디자인이 아니라 평면 PnP 기하 자체의 한계다.

**대책 (누적 적용):**

1. **지그당 태그 3개 이상을 최대한 멀리 떨어뜨려 배치**하고, **모든 태그의 코너를 한 번에
   PnP**로 푼다 (apriltag_ros의 tag bundle). 개별 태그 포즈를 평균내는 것과 완전히 다르다 —
   baseline이 길어져 회전 추정이 근본적으로 개선된다. **이 항목이 가장 효과가 크다.**
2. **측정 방향과 카메라 광축을 수직으로 배치한다.** 단일 카메라에서 광축 방향(깊이)이
   가장 부정확한 축이다. 재고 싶은 양이 이미지 평면 안의 변위가 되도록 카메라를 놓는다
   (`vision_camera_setup.md` §1).
3. **백라이트 실루엣**으로 에지를 확보한다 — 반사·조명 변화를 통째로 제거하는 가장
   비용 대비 효과가 큰 조치 (`vision_camera_setup.md` §2).
4. **태그 크기 실측값을 설정에 넣는다.** 의도한 값이 아니라 캘리퍼로 잰 값.
   크기 오차는 모든 거리에 비례 오차로 직결된다. 종이 대신 알루미늄 각인 권장.

**정밀도는 가정하지 않고 실측한다.** Phase 2의 수용 기준: 같은 지그를 10회 재설치했을 때
`T_base_rack` 재현성이 위치 σ ≤ 0.3 mm, 자세 σ ≤ 0.3°. 이 값을 못 맞추면 다음 단계로
넘어가지 않는다.

### 4.3 조립(coarse) + 정렬(fine) 2단계

마커만으로 삽입 정밀도를 내려고 하면 안 된다. 2단계로 나눈다.

```
Stage 1 (coarse, 마커):  재설치 후 T_base_rack 확보 → 안전한 접근 포즈 생성
Stage 2 (fine,  슬롯):   above 포즈에서 슬롯 자체를 관측 → 잔여 오차 보정 후 삽입
```

Stage 2가 중요한 이유: **검사용 기하 파이프라인과 정렬용 파이프라인이 같은 것**이다.
같은 ROI, 같은 평면 피팅인데, 출력이 pass/fail 대신 포즈 보정량으로 나갈 뿐이다.
하나를 만들면 둘 다 얻는다.

부수 효과: Stage 2가 동작하면 **`holder_multi_x_offsets` / `holder_multi_z_offsets` 18개
손튜닝 값이 필요 없어진다.** 매번 실측해서 보정하기 때문이다.

### 4.4 마커 부착 시 주의

- 지그의 **가공된 기준면에** 부착한다. 임의 위치에 붙이면 `T_rack_marker` 를 별도로
  측정해야 하고 그 측정이 새로운 오차원이 된다.
- 종이 인쇄물은 습기/마모로 변형된다. **알루미늄 또는 아크릴 각인/레이저 마킹**을 권장.
  재설치가 잦다면 종이는 수개월 내에 정밀도를 잃는다.
- 로봇 작업 경로와 간섭하지 않는 위치. 그리퍼가 마커를 가리면 관측 실패.
- 조명 반사가 적은 무광 표면.

## 5. 좌표계 상대 웨이포인트 리팩터 (재설치 대응의 본체)

### 5.1 현재 → 목표

```
[현재]  taught_waypoints.yaml = 관절 절대값 × 슬롯별 손튜닝 오프셋 18개
        재설치 → 전량 무효 → 10슬롯 재티칭 (수 시간)

[목표]  T_base_rack       ← 마커로 매 재설치마다 자동 측정
        T_rack_slotN      ← CAD 상수 (슬롯 피치 × N). 티칭 대상 아님
        T_slot_grasp      ← 1회 티칭. 퍽을 어떻게 잡을지. 설치 위치와 무관
        ⇒ T_base_target = T_base_rack · T_rack_slotN · T_slot_grasp → IK → 관절값

        재설치 → 마커 스캔 (~1분)
```

티칭 부담: "재설치마다 10슬롯" → "최초 1회, 영구".
슬롯 개수 변경이나 랙 교체도 CAD 상수 수정만으로 대응된다.

**⚠ 티칭이 없어지는 것이 아니다 — 티칭 대상에서 "설치 의존성"만 빠진다.**

| | 항목 | 근거 |
|---|---|---|
| ✅ 없어짐 | `holder_multi_x/z_offsets` 18개 | 6-DoF 자세 + 실시간 보정이 대체 (§4.3, `vision_camera_setup.md` §1.2.1) |
| ✅ 없어짐 | 재설치마다 하는 재티칭 | 마커가 `T_base_rack` 공급 |
| ✅ 없어짐 | 슬롯 10개 개별 티칭 | 슬롯 피치는 CAD 상수 |
| ❌ 남음 | **접근 자세** (손목 각도, 그리퍼 방향) | 측정 대상이 아니라 설계 값 |
| ❌ 남음 | **IK 분지 선택 (seed)** | 카메라가 줄 수 없다 — 아래 참조 |
| ❌ 남음 | **경로 웨이포인트** (`standby`/`above`/`retreat`) | 충돌 회피 경로. 카메라는 목표점만 알고 경로를 모른다 |

남는 항목은 **설치 위치와 무관**하므로 1회 티칭으로 영구히 유효하다.

**카메라가 줄 수 없는 것 — IK 분지.** UR3e는 한 Cartesian 포즈에 최대 8개 관절 해가 있다
(팔꿈치 위/아래, 손목 뒤집힘, 어깨 좌/우). 카메라는 "여기로 가라"만 말하고 "어떤 자세로
가라"는 말하지 못한다. 분지를 잘못 고르면 목표점은 같은데 팔이 랙을 관통하는 경로가 나온다.
그래서 기존 티칭 관절값이 **IK seed** 로 계속 필요하다 (§5.2의 최대 리스크가 이것).

**미세 보정에는 사거리 제한이 있다.** `max_correction_mm: 5.0` (§7.0). 카메라 보정은 작은
잔여 오차용이고, 개략 위치는 마커 + 상대 포즈 모델에서 와야 한다. "랙을 아무 데나 놔도
카메라가 찾아감"은 6D pose estimation / bin picking 영역의 다른 문제이며, 지그가 브레드보드
격자에 볼트 고정되는 이 응용에는 필요 없다.

**안전 측면**: 티칭 경로는 사람이 검증한 경로다. 카메라가 계산한 포즈만 믿고 팔이 자유롭게
움직이면 계산이 틀렸을 때 어디로 갈지 알 수 없다. 티칭 웨이포인트가 경계 조건 역할을 한다.

```
카메라가 공급:  T_base_rack (매번) + 미세 보정 dx,dz (매 삽입, ±5 mm 이내)
티칭이 공급:    T_slot_grasp, IK seed, 경로 구조  (1회, 영구)
CAD가 공급:     T_rack_slotN (슬롯 피치)
                       ↓
             웨이포인트 = 셋을 조합해 매번 계산
```

### 5.2 리스크 — 이 리팩터가 계획 전체에서 가장 위험하다

동작 중인 모션 코드의 핵심을 바꾼다. 완화책:

- **관절 절대 경로를 fallback으로 남긴다.** `waypoint_mode: joint | frame_relative`
  파라미터로 전환 가능하게. 새 경로가 실패하면 즉시 되돌린다.
- **IK 해 선택의 결정성 확보.** UR3e는 한 포즈에 최대 8개 IK 해가 있다. 기존 티칭 관절값을
  **seed**로 써서 같은 분지(branch)의 해를 고른다. 무작정 IK를 부르면 팔꿈치가 뒤집혀
  전혀 다른 경로가 나온다 — **이게 이 리팩터의 가장 흔한 실패 모드다.**
- **드라이런 검증**: 리팩터 후 생성된 관절값을 기존 티칭값과 비교. 같은 설치 상태에서
  차이가 관절당 0.5° 이내여야 한다. 실물 동작 전에 숫자로 확인한다.
- 단계 적용: 측정 홀더(1개) → 랙 슬롯 1개 → 전체 10슬롯 순으로 확장.

### 5.3 재설치 절차 (목표 상태)

```
1. 지그 설치 (기계 작업)
2. [외부 카메라] 로봇 베이스 마커 + 지그 마커 1프레임 → 개략 위치 확보
3. Robot:RelocalizeReq = 1
   → 로봇이 지그 마커 관측 포즈로 이동 (2단계에서 얻은 개략 위치 기반, 안전)
   → ChArUco 검출 + depth 평면 정제 → T_base_rack, T_base_measholder
   → 재현성 자체 검증 (3회 반복 측정, σ 확인)
   → 저장값 대비 변화량을 Robot:RelocalizeDelta 로 보고
4. 운영자가 변화량 확인 후 Robot:RelocalizeCommit = 1
5. 검증 사이클 1회 (실제 퍽 1개 왕복 + 전 구간 비전 검사)
```

**3번의 자체 검증과 4번의 운영자 확인을 생략하면 안 된다.** 마커 오검출로 잘못된 지그
위치를 커밋하면 그 다음 동작이 충돌이다. `RelocalizeDelta`가 사전 설정한 한계
(예: 위치 50 mm, 자세 10°)를 넘으면 자동 거부한다.

## 6. 비전 검사 설계

### 6.1 검사 지점 — 기존 waypoint에서만 촬영, 검사 전용 이동 0회

| 체크 | 시점 | 확인 항목 | 방법 | 추가 시간 |
|------|------|-----------|------|-----------|
| C1 | step 2 (`holder_above`) | 슬롯 N 점유 (F1) | 손목 or 고정 카메라 | 0.4 s |
| C2 | step 4 직후 | 파지 성공 (F2) | **GraspState** | 0 s |
| C3 | **step 8 (`sample_holder_above`)** | **측정 홀더 비었나 (F4)** | 손목 카메라 | 0.4 s |
| C4 | step 11 (`sample_holder_above_return`) | 측정 홀더 안착 (F5) | 손목 카메라 | 0.6 s |
| C5 | step 13 (`sample_holder_above_2nd`) | 아직 있나 (F6) | 손목 카메라 | 0.4 s |
| C6 | step 15 직후 | 파지 성공 (F2) | **GraspState** | 0 s |
| C7 | step 19 (`holder_above_final`) | 반환 슬롯 비었나 (F7) | 손목 or 고정 카메라 | 0.4 s |
| C8 | step 22 (`holder_above_final_return`) | 랙 안착 (F8) | 손목 카메라 | 0.6 s |
| C9 | step 3/9/14/20 실행 중 | 이상 접촉 (F9) | `ft_data` | 0 s |
| C10 | 상시 (HOLDING 중) | 낙하 (F3) | **GraspState 모니터** | 0 s |

**총 추가 사이클 타임 ≈ 2.8 s (이동 추가 0회).**

사용자가 지목한 "퍽 있는데 또 넣기"의 방어 지점은 **C3 — step 8 도착 직후, step 9로
내려가기 전**이다.

**Phase 4의 첫 작업은 FOV 실측**: 기존 `above` 포즈(= `on_position` ± 5 mm)에서 손목
카메라가 대상을 실제로 보는지 확인. 안 보이면 마운트 각도 조정 + hand-eye 재캘리브레이션.

### 6.2 외부 고정 카메라의 이중 역할

§4.1에서 M3 때문에 도입하기로 한 외부 카메라가 검사에서도 일한다:
- 한 프레임으로 **10슬롯 점유 동시 판정** → 재고 스캔에 로봇 이동 불필요
- C1/C7이 로봇 포즈와 무관해져서 **시퀀스 시작 전에** 검증 가능
  → 잘못된 홀더 번호로 트리거된 사이클을 **움직이기 전에** 거부

### 6.3 판정 상태 — `UNKNOWN`을 1급 시민으로

```
OK       기준 범위 내
NG       기준 범위 밖 (물리량 첨부)
UNKNOWN  판정 불가 — depth 포인트 부족 / ROI 미확보 / 마커 미검출 / 노출 불량
ERROR    카메라·서비스 장애
```

**`UNKNOWN`을 `OK`로 취급하지 않는다.** 정지하고 운영자에게 넘긴다. 비전 검사의 가장 흔한
현장 실패는 "판정 못 했는데 통과시킴"이다. `UNKNOWN` 발생률은 그 자체로 Phase 8(ML 투입)
여부의 판단 지표가 된다.

### 6.4 판정 알고리듬

**점유 판정**
```
1. 검사 포즈에서 depth 3프레임 중앙값 합성
2. TF(base → camera_depth_optical_frame)와 T_base_rack·T_rack_slotN 으로 ROI 투영
   → ROI가 지그 프레임에 매달림 = 재설치·캘리브 변화에 자동 추종
3. 유효 depth 포인트 비율 r < r_min → UNKNOWN
4. median depth 를 d_empty / d_occupied 와 비교, 둘 다 아니면 UNKNOWN
```

**안착 판정**
```
1. 퍽 상단면 후보 추출 (ROI ∩ 기대 높이 ±10 mm)
2. RANSAC 평면 피팅 → 법선 n, 중심 c.  inlier < N_min → UNKNOWN
3. Δz = (c − c_ref)·z_ref,  θ = angle(n, n_ref),  offset = ‖(c−c_ref) − Δz·z_ref‖
   ※ c_ref, n_ref, z_ref 전부 지그 프레임 기준 → 설치 불변
4. |Δz| ≤ dz_max AND θ ≤ tilt_max AND offset ≤ off_max → OK, 아니면 NG (초과 항목 명시)
```

**임계값은 기계 공차에서 유도한다** (경험적 튜닝 아님). 홈 깊이 1.5 mm면 `dz_max ≈ 0.7 mm`.
정상 안착 100회의 Δz 분포가 `dz_max` 대비 **4σ 이상 여유**를 갖는지 확인한다. 여유가
없으면 임계값이 아니라 기구/캘리브레이션을 고쳐야 한다.

### 7.0 픽셀 보정을 로봇 동작에 주입하는 경로

`vision_camera_setup.md` §1.2.2의 상대 측정 결과를 실제 모션에 넣는 구체적 방법.
**필요한 저수준 기구가 이미 코드에 있다.**

| 함수 | 위치 | 역할 |
|---|---|---|
| `apply_cartesian_offset_to_joints()` | `epics_triggered_sequence.cpp:1108` | TCP local 오프셋(**m**) → IK → 관절값 |
| `execute_tcp_jog(dx,dy,dz)` | `:1948` | TCP local 이동(**mm**) — 티칭 도구용 |

둘 다 `ik_frame = robotiq_hande_end` 축을 쓴다 (`:1143`, `:1979`). 픽셀 보정을 이 축으로
계산하면 좌표 변환 없이 그대로 들어간다.

```
픽셀 오차 (du,dv) → J⁻¹ → mm (dx,dz) → apply_cartesian_offset_to_joints() → 관절값
```

**픽셀↔mm 환산 (2×2 야코비안, 조깅 실측):**
```
above 포즈에서
  기준 픽셀 (u₀,v₀) 기록
  jog(+1,0,0) → (u₁,v₁) → 되돌림     ← X 열
  jog(0,0,+1) → (u₂,v₂) → 되돌림     ← Z 열
  J = [[u₁−u₀, u₂−u₀], [v₁−v₀, v₂−v₀]]      단위: 픽셀/mm
  (dx,dz) = J⁻¹ · (du,dv)
```
Y는 하강축이라 보정하지 않으므로 2×2로 충분. 카메라 내부 파라미터·`T_base_cam`·왜곡
보정을 거치지 않는다.

**함정 3개:**

1. **목표는 0이 아니다 — golden reference.** `above`에서 퍽은 슬롯 위 5 mm이므로 정상
   상태에도 픽셀 차이가 있다. 티칭 시 정상 삽입 상태의 `(u_ref,v_ref)`를 기록하고,
   운영 중에는 `du = u_now − u_ref` 로 잰다. 0으로 맞추면 안 된다.
2. **조건수로 Z 채택 여부를 결정.** 30° 비스듬이면 Z 감도가 X의 절반이라 `J` 두 열이
   가까워지면 `J⁻¹` 이 노이즈를 증폭한다.
   `cond(J) ≤ 10` → dx,dz 모두 적용 / `> 10` → dx만, dz=0 (6-DoF 모델에 맡김).
   수학이 "Z를 믿지 마라"를 알려주므로 사람이 감으로 판단하지 않는다.
3. **원본 관절값을 덮어쓰지 말 것.** 삽입 지점이 4곳(step 3/9/14/20)이고 step 20은 같은
   `j_on_pos` 를 재사용한다. 지점마다 새로 재서 **사본**에 적용한다. 덮어쓰면 누적된다.

```cpp
EXEC_CARTESIAN(2, "holder_above", j_above);
// ── 신규 ──
auto corr = request_alignment(RACK_SLOT, holder_number);
auto j_on_pos_c = j_on_pos;                      // 사본. 원본 보존
if (corr.verdict == OK) {
  j_on_pos_c = apply_cartesian_offset_to_joints(
      j_on_pos, corr.dx_m, 0.0, corr.dz_m,       // ⚠ 미터 단위
      robot_model, arm_group, ik_frame, "aligned", false);
} else if (corr.verdict != SKIP) {
  sequence_success = false; break;               // 정지
}
// ─────────
EXEC_CARTESIAN(3, "holder_on_position", j_on_pos_c);
```

**⚠ 단위**: `apply_cartesian_offset_to_joints` 는 **미터**, `execute_tcp_jog` 는
**밀리미터**. 섞으면 1000배 틀린다.

**슬롯마다 J가 다르다** — 10슬롯이 270 mm에 걸쳐 원근이 변한다. 슬롯 1/5/10에서 실측 후
선형 보간, 나머지 슬롯에서 검증. 티칭 도구가 자동 수행 (~10분).

`Align.srv`:
```
uint8 target        # RACK_SLOT / MEAS_HOLDER
uint8 slot
---
uint8 verdict       # OK / TOO_LARGE / NOT_DETECTED / ILL_CONDITIONED / SKIP
float32 dx_m        # TCP local X 보정 (미터)
float32 dz_m        # TCP local Z 보정 (미터)
float32 du_px       # 원시 픽셀 오차 (로깅·디버깅)
float32 dv_px
float32 condition   # cond(J)
string  reason
```

`config/alignment.yaml` (사이클마다 리로드):
```yaml
rack:
  jacobian:                                  # 슬롯 1/5/10 실측 → 선형 보간
    slot_1:  [[12.1, -0.4], [0.3, 5.8]]
    slot_5:  [[11.8, -0.5], [0.2, 5.6]]
    slot_10: [[11.5, -0.6], [0.1, 5.4]]
  golden:                                    # 정상 삽입 시 퍽↔슬롯 픽셀 관계
    slot_1: [412.3, 288.7]
  limits:
    max_correction_mm: 5.0
    max_condition: 10.0
```

**티칭 도구** `tools/teach_alignment.py` 는 기존 jog 인프라(`Robot:JogX/Y/Z`,
`Robot:JogStep`, `process_jog_commands()`)를 그대로 사용한다. 새로 만들 저수준 코드가 없다.

    (상태 인식이 틀린 상황의 자동 동작은 손상을 키운다)
  - **안착 불량 (F5/F8)** → 재파지 후 재삽입 **1회만**, 실패 시 정지
  - **`EMPTY`/`MISGRIP`/`DROPPED`** → 즉시 정지
  - **`UNKNOWN`** → 정지, 운영자 확인
  - **`FixtureValid=0`** → 사이클 시작 거부
  - **서비스 타임아웃/카메라 장애** → `VisionEnable=1`이면 정지, 0이면 경고 후 진행
- [ ] `VisionOverride` 강행 경로 + 감사 로그
- [ ] 기존 resume-after-crash 흐름(`CurrentStep`/`StartStep`)과 결합 검증
- [ ] `robot_gui` 검사 결과 패널 (판정, 물리량, 썸네일, 지그 상태)

### Phase 8 — ML 보조층 (조건부, 3~4주)

**투입 조건 (하나라도 만족할 때만 시작):**
- Phase 4 실측에서 `UNKNOWN` 발생률 > 2%
- gray zone(임계값 ±20%)에서 실제 오판 관측

조건 미충족 시 **실행하지 않는다. 그것이 성공이다.**

- [ ] Phase 0부터 축적된 아카이브로 데이터셋 구성 (라벨은 Layer 0~3 판정 + 운영자 확인으로
      **자동 생성되어 있음**)

- [ ] 2순위 (이상탐지로도 부족할 때만) 소형 CNN 2-class
- [ ] ONNX Runtime CPU, < 100 ms
- [ ] **권한 제약을 타입/API로 강제** (§3.3): `NG → OK` 덮어쓰기 경로가 코드에 존재하지
      않도록. 런타임 `if` 가드가 아니라 구조로 막는다
- [ ] 골든 데이터셋 회귀 테스트 (모델 교체 시 필수 통과)

### 9.1 순서에 대한 판단 — 사용자 결정 필요

Phase 5(리팩터)를 Phase 4 뒤에 둔 이유: 동작 중인 모션 코드를 건드리는 최대 리스크
작업이므로, 검증 수단(비전 검사)을 먼저 갖춘 뒤에 하는 것이 안전하다. 리팩터 결과를
비전으로 검증할 수 있게 된다.

**단, 재설치 주기가 월 1회보다 잦다면 이 순서를 뒤집는 것이 맞다.** 그 경우 Phase 4보다
Phase 5를 먼저 하고, 매 재설치마다 10슬롯을 재티칭하는 비용을 먼저 없앤다.
→ **실제 재설치 주기를 알려주시면 순서를 확정하겠습니다.**

## 11. 미확인 사항 (착수 전 확인 필요)

1. **퍽 치수** — 직경, **파지 직경**, 두께, 랙 슬롯 홈 깊이, 측정 홀더 안착면 형상.
   → `stroke_puck`, `dz_max`, `tilt_max`, `off_max` 가 전부 여기서 유도된다. **최우선.**
2. **랙 슬롯 피치와 가공 도면** — Phase 5의 `T_rack_slotN` CAD 상수의 근거.
   도면이 없으면 실측으로 대체해야 하고 정밀도가 떨어진다.
3. **실제 재설치 주기** — §9.1의 순서 결정 입력.
4. **D405 실제 마운트 위치/각도** — 현재 `~/calibration_data/hand_eye_calibration_latest.yaml`
   내용 확인 필요 (이 저장소에 없음).
5. **D405 근거리 실측 노이즈** — 데이터시트 값이 아니라 이 조명·이 알루미늄 표면에서의
   실측. Δz 판정의 SNR이 여기 달림. Phase 0에서 측정.
6. **UR3e 내장 FT 분해능/정확도** — 데이터시트 확인. §2.2의 차분 측정 하한을 정한다.
7. **현재 실패 빈도** — F2/F4/F5/F8 각각 사이클당 몇 %인지.
8. **외부 고정 카메라 설치 공간** — 로봇 작업영역·재설치 시 간섭 없이 랙 정면을 볼 수 있는지.
9. **측정 홀더 형상** — 사진상 원형 링 시트로 보이는데 키홈/회전 정렬 요구가 있는지.
